# 项目日报（2026-09-02）

## 1. 运行与环境问题

- 问题：直接执行 conda activate opennav 报 shell 未初始化。解决：先 source /root/miniconda3/etc/profile.d/conda.sh，再执行 conda activate opennav。状态：已解决。
- 问题：run_harness_tool() 同时收到位置参数和关键字 step_id，smoke 在第 0 步崩溃。解决：统一工具调用的参数传递方式，消除重复 step_id。状态：已解决。
- 问题：本地模型路径 /root/models/Qwen3.5-4B 被 llmClient 判为未知模型类型。解决：本地 Qwen 路径按 OpenAI-compatible 模型处理，不再只接受 Qwen/... 名称。状态：已解决。

## 2. 主 Pipeline 与状态语义

- 问题：旧 completion 与 ACN 同时承担进度判断，形成双重进度源。解决：移除 LLM completion 在线判定，ACN L1 成为唯一 ProgressProvider。状态：已解决。
- 问题：ProgressUpdate.complete 同时表示路线完成和目标完成，导致路线完成后过早提出 STOP。解决：拆成 route_progress_complete、terminal_target_confirmed、goal_complete。状态：已解决。
- 问题：普通 plan 目标不可检查，Anchor Chain 只是文本拆分。解决：Anchor Chain v2 改为可观测 route anchors 与独立 terminal policy。状态：已解决。
- 问题：终点描述中的逗号会把限定语拆成新 anchor。解决：增加终点子句合并规则。状态：已解决。
- 问题：主循环同时承担状态、规划、STOP 和动作编码。解决：已完成 M0-M3 契约、StateReducer、单一 ProgressProvider、StopCoordinator 和 ActionCompiler 的阶段性拆分。状态：阶段性完成，M4 旧旁路清理待后续。

## 3. STOP 与动作链问题

- 问题：Habitat action 0 同时可能表示 goal STOP 或 operational termination。解决：上游区分 goal_stop 与 forced_termination，由 ActionCompiler 统一编码并保留终止原因。状态：已解决。
- 问题：旧 proactive STOP 条件过早，97 步产生 33 个 proposal，且同一步第二次调用 V2。解决：proactive 改为 diagnostic hint、decision_effect=false；每步只生成一份 TerminalEvidence。状态：已解决。
- 问题：final_target_visible/arrival=true 在 V2 reject 或 not_applicable 时仍可能形成 goal_complete。解决：正式确认必须通过 V2/策略 verdict、可见性、arrival、方向 RGB-D、实例连续性和路线状态。状态：已解决。
- 问题：StopCoordinator 未把 V2 和 progress 作为硬约束。解决：正式 required/opposing evidence 改为 v2 + progress。状态：已解决。
- 问题：legacy_combined 构成循环证据。解决：退出正式 required/opposing 集合，仅保留兼容日志。状态：已解决，adapter 待删除。
- 问题：selector、completion、proactive 曾存在多条 STOP 支路。解决：StopProposal 统一进入 StopCoordinator，ActionCompiler 成为 action=0 唯一出口。状态：已解决。
- 问题：同一步已有 STOP reject 后再请求 forced termination 会产生决策冲突。解决：合并既有 proposal/evidence，在空 movement 集合上重新仲裁。状态：已解决。
- 问题：MOVE_BACK 是合成动作，却按普通候选读取 observe_dict/save_history，先后出现 KeyError 和 ValueError。解决：MOVE_BACK 使用结构化 synthetic history。状态：已解决。

## 4. 终点视觉、空间与实例问题

- 问题：视觉证据只绑定目标类别，附近另一个同类 archway 可复用旧证据。解决：新增 TerminalInstanceTracker，根据目标词、方向、Depth、位姿生成稳定 instance_key；实例变化立即清空缓存。状态：已解决第一阶段。
- 问题：连续两帧 visible 不能证明是同一目标。解决：正式 persistence 改为同一 instance_key 连续观测至少 2 次。状态：已解决。
- 问题：文本可能来自全景其他方向，而图像/Depth 来自 target_direction_id。解决：只读取同一 selected candidate 的目标词、可见性、arrival 和 direction；全景聚合值仅用于审计。状态：已解决。
- 问题：开口中心射线会穿过门洞读到远墙。解决：开口类使用目标方向宽区域近表面 p20，普通目标使用中心中位数，并同时记录两种值。状态：临时解决。
- 问题：方向区域 Depth 并非目标实例 mask 的 Depth。解决：字段改为 local_surface_depth_m，并声明 direction_local_surface_not_instance_mask；必须结合稳定实例轨迹。状态：部分解决，完整方案仍需 bbox/mask。
- 问题：终点证据与 ACN route complete 错开 1-2 步，导致正确目标无法停止。解决：TerminalEvidenceMemory 最多保留 2 步、位移不超过 2.25m，且只允许相同 instance_key 复用。状态：已解决。
- 问题：弱通用目标即使类别、文本和近距离成立仍可能认错实例。解决：增加 weak_generic 分类和路线成熟度门。状态：临时安全门已实现。
- 问题：路线成熟度最初累计命令距离，碰撞或未执行也会增长。解决：改为 envs.step 后实际位移，只统计无碰撞且位移大于 0.05m 的前进步。状态：已解决。
