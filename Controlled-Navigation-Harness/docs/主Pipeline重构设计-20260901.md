# 主 Pipeline 重构设计：RouteState 驱动的单一状态链

> 本文定义下一代主导航 pipeline 的目标架构和迁移顺序。它是设计提案，不表示代码已经实现，也不表示 ACN 已产生在线收益。
>
> 目标不是一次性替换整套导航器，而是消除双重进度源、分散状态所有权和多条 STOP 支路，使每个在线干预都能单独启用、回放和回滚。

## 0. 决策摘要

```text
ObservationFrame
  -> StateReducer
  -> RouteState
  -> DecisionContext
  -> ActionPlanner + StopCoordinator
  -> ActionCommand
  -> TransitionReducer
  -> 下一步 RouteState
```

- `RouteState` 是跨步、跨模块共享的唯一外部事实状态；
- `ProgressProvider` 是 progress 的唯一写入者，同一步不能有两个在线进度源；
- `DecisionContext` 是 RouteState 和本步候选的只读决策投影；
- `StopCoordinator` 是唯一可以提交或拒绝 STOP 的组件；
- `DecisionRecord` 记录模型输出、候选评分、门控和最终动作，不充当事实状态；
- simulator 目标距离、success、OSR 只进入 `AuditRecord`。

当前 M2 目标已经收口：ACN L1 是唯一进度提供器，不再保留 shadow、legacy completion 或回退路径；其他 ACN 模块仍按单变量方式逐步开放决策权。

## 1. 当前主链的结构性问题

### 1.1 双重进度源（已在 M2 解决）

旧链每步先调用 `navigator.estimate_completion()`，再用 L1 文本覆盖，造成两个在线进度源。M2 已删除该调用和 legacy adapter；当前只由 `ACNL1ProgressProvider` 生成结构化权威进度。

### 1.2 RouteState 是快照，不是事实总线

L1、M1、M2、phase、V2、candidate prior 和 fallback 仍通过局部变量或模块实例连接。RouteState 在链路末端聚合结果，但下游没有统一只读它。“记录完整”不等于“状态驱动决策”。

### 1.3 STOP 有多个支路

completion STOP、selector STOP、proactive STOP、V2、depth veto 和 L4 分散在不同分支。相同证据可能重复计算，同一个 STOP 也可能经过不同次序的门控。

### 1.4 持久事实与策略输出混杂

锚点、进度、空间图和地标池属于跨步事实；LLM thought、candidate prior、fallback ranking 和 verifier verdict 属于单步决策过程。两者必须分离，避免 RouteState 随策略改变而失去跨实验可比性。

### 1.5 大循环职责过多

训练器同时负责生命周期、模型调用、候选构造、进度估计、停止门、fallback、动作编码、环境执行和日志，单点修改容易跨越多个决策面。

## 2. 设计原则

### 2.1 单一写入者

| 状态字段 | 唯一写入者 | 其他模块权限 |
|---|---|---|
| `plan` | `PlanBuilder`（L0） | 只读 |
| `progress` | 当前 `ProgressProvider` | 只读，不得直接改 `j` |
| `spatial_graph/loop_status` | `SpatialGraphReducer`（M1） | 只读 |
| `landmark_memory` | `LandmarkReducer`（M2） | 只读 |
| `failure_status` | `FailureReducer` | 只提交可观测事件 |
| `budget` | `BudgetReducer` | 只读 |
| `stop_evidence` | `StopCoordinator` | verifier 只返回证据项 |

### 2.2 事实与策略分离

- `RouteState`：跨步事实及 provenance；
- `DecisionContext`：本步给规划器看的最小投影；
- `DecisionRecord`：本步策略输出和覆盖链；
- `AuditRecord`：仅评估可见的 oracle 指标。

DecisionRecord 可以引用 `route_state_id`，但不能修改已经提交的 RouteState。动作后的可观测结果通过 `TransitionReducer` 生成下一版本状态。

### 2.3 显式策略，不用隐式布尔组合

```yaml
PIPELINE:
  VERSION: route_state.v2
  PROGRESS_PROVIDER: acn_l1
  STOP_POLICY: coordinated_v1
  LOOP_POLICY: observe_only       # observe_only | context_alert
```

非法组合在启动时失败。例如 `PROGRESS_PROVIDER=acn_l1` 但 L1 未启用，必须报错，不能静默退回 LLM。

### 2.4 决策链不得读取 AuditRecord

从代码边界上让在线对象无法接触 `info.distance_to_goal`、success 或测地距离，而不是只依赖字段过滤。AuditRecord 在动作完成并提交在线状态后单独构造。

### 2.5 单一 ACN L1 provider

LLM completion 已从目标和实现中删除。ACN L1 是唯一权威进度源；链退化或证据不足时输出 abstain，禁止静默调用 LLM 或 rule fallback。

## 3. 目标对象契约

### 3.1 ObservationFrame

```text
episode_id, step_id
instruction / parsed plan reference
agent pose and heading
RGB-D observation references
CandidateState[]
RAM / SpatialBot observable outputs
previous ActionReceipt
```

不包含 simulator 目标状态和 episode 成功标签。

### 3.2 RouteState v2

```text
schema_version: route_state.v2
state_id, parent_state_id
episode_id, step_id, revision
stage: observed | decision_ready | transitioned
plan, progress, spatial_graph, landmark_memory
loop_status, budget, failure_status, stop_evidence
last_action_receipt, provenance
```

每个可影响决策的分区至少包含：

```text
source, confidence, abstained, decision_effect
updated_at_step, evidence_refs[]
```

RouteState 不保存 LLM thought、完整 prompt、候选 prior 分数或 oracle metrics。

### 3.3 ProgressProvider

```python
class ProgressProvider:
    def reset(plan) -> None: ...
    def update(frame, previous_progress) -> ProgressUpdate: ...
```

`ProgressUpdate` 包含：

```text
provider: acn_l1
current_index / total, completed_indices, current_target, complete
confidence, abstained
transition: advance | hold | correct | abstain
evidence_refs
display_text  # 仅兼容旧 prompt，不是权威状态
```

运行时只允许 `acn_l1`。L1 的结构化定位结果经 provider 转换为唯一权威
`ProgressUpdate`；证据不足时明确 `abstain`，不会调用 completion LLM，也不会切换到
规则或文本型后备实现。

### 3.4 DecisionContext

由 `ContextProjector` 从 `RouteState(stage=decision_ready)` 和候选观察生成：

```text
route_state_id, current_target, verified_history, progress_status
candidate_observations, candidate_ids, landmark_summary, loop_summary
budget_summary, failure_summary, allowed_action_types
```

所有 selector 使用同一个 DecisionContext。任何 context augmentation 都必须产生具名字段和 evidence reference。

### 3.5 StopProposal、EvidenceItem 与 StopDecision

所有模块只能表达停止意图，不能写 `stop_flag`、`next_vp=STOP` 或环境 action 0。

```text
StopProposal
  proposal_id, source, kind
  route_state_id, step_id, reason
  evidence_refs[], priority
```

`kind` 只有两类：

- `goal_stop`：模块认为导航目标已满足，必须经过到达证据门；来源包括 `progress_completion`、`proactive_visual`、`selector`；
- `forced_termination`：不存在合法移动、预算硬耗尽或不可恢复执行错误；不宣称到达目标，不通过 V2/L4 冒充成功。

验证器只产生不可变证据项：

```text
StopEvidenceItem
  evidence_id, proposal_id, evaluator
  verdict: support | oppose | abstain
  confidence, reason, observable_inputs[]
  thresholds_version, evidence_refs[]
```

协调器是纯函数：

```python
StopDecision = StopCoordinator.resolve(
    route_state, proposals, evidence_items, movement_candidates, policy
)
```

输出契约：

```text
StopDecision
  decision_id, route_state_id, step_id
  outcome: commit_goal_stop | commit_forced_termination | reject | no_request
  selected_proposal_id, reason
  consumed_evidence_ids[], rejected_proposal_ids[]
  fallback_required, policy_version
```

只有 `commit_goal_stop` 或 `commit_forced_termination` 可以由 `ActionCompiler` 生成 STOP `ActionCommand`。`reject` 必须回到已有候选的确定性 movement fallback，不能再次调用 selector LLM。

### 3.5.1 单步只裁决一次

- pre-planner 阶段收集 progress/proactive proposal；存在请求时统一裁决：批准则跳过 planner，拒绝则调用只允许 movement 的 planner；
- 没有 pre-planner 请求才调用 selector；selector 返回 STOP 时形成 proposal，并进行本步唯一一次裁决；
- 同一 proposal 不得重复运行 V2、depth 或 L4；相同观测派生的共享证据允许被多个 proposal 引用；
- STOP 被拒后不得产生第二个 goal-stop proposal。

### 3.6 DecisionRecord 与 ActionReceipt

DecisionRecord 记录 route_state/context 版本、planner 原始输出、STOP 门控、fallback/prior/backtrack 覆盖链、原始和最终候选，以及最终 ActionCommand。

`envs.step()` 后归一为 ActionReceipt：

```text
command_id, executed_action, pose_before / pose_after
collision / displacement / done, candidate_id
observable_failure_events
```

目标距离变化和 success 不进入 ActionReceipt，只进入之后的 AuditRecord。

## 4. 新主链时序

### 4.1 Episode 初始化

```text
解析 instruction
  -> PlanBuilder 生成一次 plan
  -> ProgressProvider.reset(plan)
  -> M1/M2/Failure/Budget reducers reset
  -> RouteState(stage=initialized, revision=0)
```

Reducer 必须接收 episode_id；同 episode 重复初始化应幂等，不同 episode 不允许复用 mutable state。

### 4.2 每步在线链

```text
1. collect_observation() -> ObservationFrame
2. StateReducer.observe(frame, previous_state)
     更新 M1/M2、progress、loop/failure/budget
   -> RouteState(stage=decision_ready)
3. ContextProjector(route_state, candidates) -> DecisionContext
4. StopProposer / ActionPlanner 产生提议
5. StopCoordinator 统一裁决 STOP
6. CandidatePolicy 执行已注册、可审计的 override
7. 输出一个 ActionCommand，同时写 DecisionRecord
8. envs.step(ActionCommand) -> ActionReceipt
9. TransitionReducer(route_state, receipt)
   -> RouteState(stage=transitioned)
10. 独立写 AuditRecord
```

一次循环只能提交一个 ActionCommand；它必须引用唯一的 route_state_id 和 decision_record_id。

### 4.3 决策与覆盖的固定次序

```text
progress/proactive proposers
  -> pre-planner StopCoordinator（有 proposal 时）
  -> ActionPlanner（未提交 STOP；若已拒停则 allowed_action_types=move）
  -> selector StopProposal（若 planner 返回 STOP）
  -> StopCoordinator（本步尚未裁决时）
  -> legality filter
  -> deterministic movement fallback（STOP 被拒或候选非法）
  -> candidate prior（仅配置允许）
  -> backtrack resolver
  -> ActionCompiler
```

`ActionCompiler` 是环境动作的唯一写入者。prior/backtrack/fallback 只能选择 movement，不能生成 goal STOP；空动作空间只能提交 `forced_termination` proposal，再由 coordinator 裁决。

每次变更进入类型化 `OverrideEntry`：

```text
override_id, stage, policy, reason
input_candidate, output_candidate
input_action_type, output_action_type
evidence_refs[], action_affecting
```

ledger 必须满足链连续性：后一项 input 等于前一项 output，最后一项 output 等于 `ActionCommand.candidate_id`。

## 5. ACN 在新主链中的位置

| ACN 部件 | 新职责 | 是否直接选动作 |
|---|---|---:|
| L0 | `PlanBuilder` | 否 |
| L1 | `ProgressProvider(acn_l1)` | 否，只写 progress |
| M1 | `SpatialGraphReducer` | 否，可实验性提供 loop summary |
| M2 | `LandmarkReducer` | 否，为 progress/STOP 提供证据 |
| L4 | `StopEvidencePolicy` | 否，只返回 StopCoordinator 的一项判定 |

ACN 不是另一个并列导航器。Planner 仍从候选中选动作，但读取统一状态投影，而不是多个 ACN 临时字符串。

### 5.1 Anchor Chain v2（2026-09-02 已落地）

L0 不再把以 `Stop/Wait/Stay/Pause` 开头的动作放入 L1 进度队列，即使该动作
同时携带目标描述。终止指令及其中的最终目标属于 `terminal_policy`；最后一个
非终止 Anchor 只标记为 `terminal_predecessor=true`。

```text
actions + landmarks
  -> 去除列表编号
  -> 分离 terminal directive
  -> 构造可验证 anchors
  -> 最后一个非终止 anchor = terminal_predecessor
```

Anchor v2 将验证条件写入 Anchor Contract：

```json
{
  "kind": "object",
  "key": "sofa",
  "parse_status": "parsed",
  "terminal_target": true,
  "verification": {
    "predicate": "object_nearby",
    "parameters": {"max_waypoint_distance_m": 3.0, "min_consecutive_hits": 2},
    "on_unverifiable": "abstain"
  }
}
```

| kind | predicate | 证据与迟滞 |
|---|---|---|
| `location` | `location_dominant` | RAM 房间标签占比不少于 0.5，连续 2 步 |
| `object` | `object_nearby` | RAM 目标标签且 waypoint 不超过 3m，连续 2 步 |
| `direction` | `odometry_motion` | 跨步位姿/朝向窗口，命中 1 次 |
| `unknown/unsupported` | `unverifiable + skip` | 有动作语义但无验证器，显式跳过并审计 |
| `unknown/parse_failure` | `unverifiable + abstain` | 无法解析，不得静默推进 |

`terminal_policy.predicate=coordinated_stop` 仅声明终止条件；当前 L4 仍为
`LOG_ONLY=true`，不会扩大 STOP 权限，最终 STOP 继续由 `StopCoordinator` 决定。

### 5.2 路线完成与目标完成拆分（2026-09-02 已落地）

`ProgressUpdate.complete` 仅保留为路线进度的兼容别名，任何 STOP 模块不得读取它。
权威语义拆分为：

```text
route_progress_complete
  = ACN L1 已验证全部非终止 Anchor

terminal_target_confirmed
  = 最终目标连续两步可见，且当前帧存在 arrival evidence

goal_complete
  = route_progress_complete AND terminal_target_confirmed
```

只有 `goal_complete=true` 才允许生成 `progress_completion` StopProposal。旧
`navigator.should_stop()` 暂时保留为诊断器，其结果写入
`legacy_completion_requested`，但不再拥有 proposal 权限。

每步先写 ACN 路线状态，再在视觉证据生成后写最终事件：

```text
pipeline_progress_update       # 路线状态
pipeline_goal_progress_update  # 路线 + 终点证据的最终合取状态
```

Proactive visual STOP 是独立 proposal 来源，不被合并进 ACN L1。

## 6. 唯一进度链

```text
RouteStateReducer.update_progress(observation)
  -> ACN L1 locator_state
  -> ACNL1ProgressProvider.update(locator_state)
  -> authoritative ProgressUpdate
  -> RouteState.progress + compatibility display_text
  -> phase / STOP / selector
```

约束：

1. 每一步最多生成一个权威 `ProgressUpdate`；
2. provider 只接受本 episode 已 reset 的 L1 状态；
3. index 不允许倒退，异常倒退直接报错；
4. 无充分证据时输出 `transition=abstain`，不伪造 advance；
5. `display_text` 只服务尚未结构化的下游 prompt，不具备权威性；
6. completion LLM、shadow provider 和 rule fallback 均不在运行图中。

后续模块按单变量顺序开放决策权：先稳定 L1 progress，再评估 L4 guarded STOP、
M1 loop context，最后才做组合实验；不得使用无法归因的“ACN enabled”总开关。

## 7. M3：统一 STOP 裁决

### 7.1 当前来源到新契约的映射

| 当前路径 | 新 proposal source | kind | 是否需要到达证据 |
|---|---|---|---:|
| ACN progress 完成判断 | `progress_completion` | `goal_stop` | 是 |
| proactive visual arrival | `proactive_visual` | `goal_stop` | 是 |
| selector 输出 STOP | `selector` | `goal_stop` | 是 |
| backtrack 失败且无候选 | `no_movement_candidate` | `forced_termination` | 否 |
| action-space 为空 | `empty_action_space` | `forced_termination` | 否 |
| 环境返回 done | 不产生 proposal，写 ActionReceipt | — | 否 |

旧名称 `completion_gate` 只作为日志兼容别名，代码对象统一使用 `progress_completion`。

### 7.2 证据只计算一次

每步生成 `StopEvidenceSnapshot`，包含 V2 current-pano、depth、L4、progress 和视觉持久性证据。proposal 通过 evidence id 引用快照，不复制可变 dict，也不重复调用 VLM。

- V2 明确 `oppose`：拒绝 goal STOP；
- depth 超阈值为 `oppose`；depth 不可用为 `abstain`，不伪装 support；
- L4 仅在配置为 action-affecting 时是必需合取项；
- 任一必需证据 `oppose` 即拒绝；必需证据 `abstain` 的处理必须由具名配置决定，默认拒绝；
- `forced_termination` 只验证确实没有合法 movement，不消费到达证据。

### 7.3 多 proposal 处理

同一步允许多个 proposer 提交意图，但只有一个 StopDecision：

1. 丢弃 route_state_id/step_id 不匹配的 proposal；
2. 分别评估每个 goal proposal 的必需证据；
3. 若多个 proposal 获准，按固定优先级 `progress_completion > proactive_visual > selector` 选择 provenance；
4. goal proposal 全被拒且仍有 movement 时返回 `reject + fallback_required`；
5. 只有 movement 集为空时，才允许 `forced_termination`；
6. 不允许用 forced termination 覆盖一个仍可执行的 movement。

优先级只决定日志中的主 proposal，不改变环境动作。

### 7.4 STOP 被拒后的唯一出口

```text
pre-planner StopDecision(reject)
  -> movement_required event
  -> ActionPlanner(allowed_action_types=move)

selector StopDecision(reject)
  -> movement_required event
  -> DeterministicMovementFallback.rank(existing ranked candidates)

两条路径汇合
  -> legality filter
  -> movement ActionCommand
```

selector STOP 被拒后不得再次调用 selector；pre-planner STOP 被拒后允许且只允许一次 movement-only planner 调用。任何路径都不得重新提出 proactive STOP，不得由 backtrack/prior 把 movement 改回 STOP。若 fallback 后候选变空，提交一个 `forced_termination` proposal，并在同一 DecisionRecord 中记录这是 operational termination，而非导航成功。

### 7.5 ActionCompiler 边界

训练器不再直接构造 action 0/4。`ActionCompiler` 接收最终 `ResolvedAction`：

```text
ResolvedAction(type=stop, stop_decision_id=...)
ResolvedAction(type=move, candidate_id=..., angle=..., distance=...)
ResolvedAction(type=backtrack, action_args=...)
```

编译规则固定：stop -> action 0，move/backtrack -> action 4。stop 缺少已提交 StopDecision、move 缺少合法 candidate 或任一引用版本不匹配时立即报错。

### 7.6 DecisionRecord 与日志

每步必须记录：全部 proposals、evidence snapshot、唯一 StopDecision、planner 是否被跳过、完整 override ledger、最终 ActionCommand。旧 `stop_decision`、`visual_stop_rejected`、`terminal_gate_rejected` 事件可以暂时保留，但只能由统一记录派生，不能再各自驱动行为。

推荐新增事件：

```text
pipeline_stop_proposal
pipeline_stop_evidence
pipeline_stop_decision
pipeline_override_entry
pipeline_action_command
```

### 7.7 失败与降级语义

- `acn_l1` 初始化失败：终止运行或 episode，不能静默调用 LLM；
- 必需 STOP evaluator 异常：按 `abstain` 处理并记录 tool failure，禁止伪造 allow；
- 辅助 reducer 失败可保留上一状态并标记 stale；
- STOP 被拒后只生成一次 `movement_required`；
- 没有 movement 时允许 operational STOP，但 termination reason 必须是 `forced_termination`，评估层不得把它解释成成功。

### 7.8 M3 实施切片

1. **M3.0 契约**：扩展 StopProposal，新增 StopEvidenceItem、StopDecision、OverrideEntry、ResolvedAction；
2. **M3.1 纯协调器**：用冻结 trace 做纯函数测试，暂不接管 action；
3. **M3.2 goal STOP 接管（已完成第一版）**：progress/proactive/selector 的最终 goal STOP 由 coordinator 唯一裁决，旧 gate 通过 evidence adapter 接入；
4. **M3.3 action compiler 接管（已落地待 smoke）**：训练器只生成 ResolvedAction，由 ActionCompiler 唯一编码 action 0/4；空候选和 backtrack 耗尽纳入 forced termination；
5. **M3.4 删除旁路**：删除分散 `stop_flag` 改写、重复 V2/depth/L4 调用和 STOP 拒绝后的第二次 selector。

每个切片单独提交并跑固定 episode replay；M3.1 必须行为等价，M3.2 之后才允许有经解释的行为变化。

### M0：抽取契约，不改变动作

新增核心对象，用 adapter 包装当前模块，并对旧 pipeline 做 golden trace 对比。

通过条件：同输入最终动作完全一致，对象可序列化且无 oracle。

### M1：建立 StateReducer

把 L0/L1/M1/M2 生命周期移到 episode-scoped reducer；RouteState v2 成为唯一跨步快照。

通过条件：跨 episode 无泄漏；事件重放得到相同状态哈希。

### M2：统一 progress provider

实现唯一 `acn_l1` provider；不产生 completion LLM 调用；下游通过结构化 ProgressUpdate 和兼容 display_text 消费进度。

通过条件：不存在“L1 生效但仍调用 completion LLM”。

### M3：统一决策与 STOP

按 M3.0–M3.4 实施：先扩展契约和纯协调器，再依次接管 goal STOP、环境动作编译与 operational termination，最后删除分散旁路。所有 proposer 只产生 StopProposal，验证器只产生 StopEvidenceItem，只有 StopCoordinator 可以产生已提交 StopDecision，只有 ActionCompiler 可以编码 action 0。

通过条件：

- 每个 STOP/拒停可由一个 DecisionRecord 完整还原；
- 每步至多一个 StopDecision 和一个 ActionCommand；
- 源码中 action 0 只存在于 ActionCompiler；
- STOP 拒绝后没有第二次 selector LLM 调用；
- forced termination 与 goal stop 在 trace 和评估中可区分；
- 不存在任何 `stop_flag=True` 或 `next_vp=STOP` 的旁路提交。

### M4：删除旧旁路

在 M3 接管 STOP 后，删除剩余训练器内 ACN mutable state、无事件 prompt 拼接、兼容 display_text 直读和旧隐式布尔组合。

## 10. 测试与上线闸门

### 10.1 单元不变量

1. 一个 episode 只初始化一次 plan/reducer；
2. 同一步只有一个权威 ProgressUpdate；
3. `acn_l1` 的 completion LLM 调用数为 0；
4. 在线对象不含 oracle 字段；
5. 每个 ActionCommand 引用存在且版本匹配的 RouteState/DecisionRecord；
6. 每步至多一个 StopDecision，STOP 只能由已提交 decision 编译；
7. 任一必需证据 oppose 后，goal STOP 不得提交；
8. L4 action-effect 开启且拒绝时，最终命令不能是 STOP；
9. selector STOP reject 后恰好一次 deterministic movement fallback，selector 调用数不增加；
10. pre-planner STOP reject 后至多一次 movement-only planner 调用，且不能返回 STOP；
11. 有合法 movement 时不得提交 forced termination；
12. override ledger 链连续且末端等于最终 ActionCommand；
13. 源码静态检查保证训练器无 action 0 直写和 stop_flag 旁路；
14. ObservationFrame + ActionReceipt 重放得到相同状态哈希。

### 10.1.1 StopCoordinator 真值测试

| proposal | 必需证据 | movement | 期望 outcome |
|---|---|---:|---|
| 无 | — | 有 | `no_request` |
| goal | 全 support | 任意 | `commit_goal_stop` |
| goal | 任一 oppose | 有 | `reject` |

M0/M1 的行为兼容已经由纯模块和静态接线测试约束；M2 是明确的单变量行为变更，必须用固定 episode 列表与此前 resolved config 做配对比较。

### 10.3 上线闸门

## 11. 本次重构范围外

- 不更换 backbone、waypoint predictor 或动作空间；
- 不引入 BEV、TSDF 或学习型 belief；
- 不同时调整预算、V2 阈值、candidate prior 或 backtrack；
- 不以速度收益替代导航质量验证；
- 不把 RouteState 变成包含所有日志的巨大对象；
- 不在同一实验中同时开放未经单变量验证的其他 ACN 决策权。

## 12. 完成定义

```text
每步一个权威 RouteState
+ 每类状态一个写入者
+ 每步一个 DecisionRecord
+ 每步一个最终 ActionCommand
+ STOP 无旁路
+ 在线链无法读取 AuditRecord
+ progress provider 互斥且不重复调用
+ 同一 trace 可确定性重放
```

工程完成不等于 SR 提升。研究结论仍需单变量配对实验回答：L1 是否减少错误进度，L4 是否把假停转为有效继续而非耗尽，M1 是否降低重复重访。
