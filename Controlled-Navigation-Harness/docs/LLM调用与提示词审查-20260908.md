# LLM 调用与提示词审查

**记录时间：** 2026-09-08  
**目的：** 让模型负责理解和选路，让动作完成与正式停止继续由可检查的状态和证据决定。本文区分已修改的程序行为和尚未经过在线实验验证的效果。

**后续修订：** EP10 暴露了一次性解析的语义错误，已改回“动作提取 → 地标与终点提取”两个顺序请求。详见[两步指令解析修复记录](指令两步解析修复与验证-20260908.md)。下文的旧实验结果保留为历史记录。

## 一、目前到底有几处需要模型

“两处”现在适用于**文本决策职责**，不适用于整套系统的所有模型推理。

| 职责 | 修改前 | 修改后 |
|---|---|---|
| 理解指令 | 曾改为一次联合请求 | 恢复两个顺序请求：先完整动作，再基于原指令和动作提取地标与主终点；同版本缓存命中为零调用 |
| 每步选择下一步 | 默认一次选路请求 | 默认仍为一次，使用当前动作与 ACN 验证反馈 |
| 记录历史 | 普通移动后两次模型摘要 | 零调用，直接记录动作前观测、选择理由和执行回执 |
| 合并与确认候选 | 多候选分歧时追加模型调用 | 零调用，按票数排序、候选白名单过滤；同票保持原顺序 |
| ACN 动作完成 | 代码验证 | 不变，不新增 LLM completion |
| 候选图像证据 | Qwen 视觉请求 | 保留，通常每步一次批量请求，不是每张图片一次 |
| 当前全景终点证据 | Qwen 视觉请求 | 保留，按停止链需要触发，同一步复用结果 |
| 场景描述 | 每个候选方向的本地 SpatialBot RGB-D 推理 | 保留；RAM 标签提取也保留，RAM 本身不是文本大模型 |

指令理解由 `get_plan()` 顺序调用两个提取阶段，每阶段最多一次纠错重试，正常为两次请求，最多四次；选路仍由 `move_to_next_vp()` 负责。默认选路 `k=1`；若其他实验显式使用 `k>1`，选路请求次数仍会增加，但不再追加融合/仲裁请求。网络重试与启动时的服务探活另计。

**不能为了得到“整个系统只有两次模型调用”而直接关闭 visual_evidence：它目前仍被正式终点验证链消费。** `LOG_ONLY=True` 只表示证据生产器本身不直接执行动作，不能推导出其输出不会影响 STOP。

## 二、发现的问题与修改方法

### 2.1 一次性计划解析未能稳定保留终点含义（原方案已替换）

最初担心第二步只读取动作文本会丢信息，因此尝试合并生成。但实际 EP10 的 EP513 把一个复合停止条件拆成两个 STOP，说明减少一次请求并未保证语义正确。当前恢复两步，并让第二步同时读取原指令和已校验动作，显式输出主停止位置。

~~~text
Stop in the doorway to the left of the white double doors

最终位置：doorway
定位参照：white double doors
不能把参照物当成最终停止目标。
~~~

**当前解决方法：** 第一阶段只生成 `actions`；第二阶段生成 `landmarks` 和 `terminal_target`。程序检查完整停止原文、主终点及参照物，并保持最终目标位于地标列表末尾。以下是传给下游的合并展示，实际由两个请求产生：

输出示例：

~~~json
{
  "actions": [
    "Go through the door",
    "Turn left",
    "Go to the left of the stairs",
    "Stop in the doorway to the left of the white double doors"
  ],
  "landmarks": ["door", "stairs", "white double doors", "doorway"]
}
~~~

`actions`、`landmarks` 均为字符串数组；动作不能为空，纯转向指令允许地标为空。第二阶段另外返回 `terminal_target:string|null`，用于检查主终点。程序将结果转换为原有两段逐行文本，供 Anchor Chain 和其他模块使用。计划版本为 `opennav.instruction_plan.v2.two_stage`，Anchor Chain schema 不变。

**实施中处理的问题：** 缓存指纹现在包含两个阶段的提示词、模型、服务地址和格式版本；旧联合解析缓存保留但不复用。失败阶段最多重试一次；仍失败时明确记录原始响应和原因、关闭环境，不缓存半份计划。真实模型常把移动与 STOP 写在同一项，程序会无损分离；完整终点描述包含参照关系时，保留原描述并明确主终点。

**当前状态：两步实现已替换旧方案，119 项回归通过；真实 Qwen 的固定十条指令通过本次终点保留与跨模块一致性检查。** 这不能证明整个路线都已被正确理解，也不是新一轮导航成功率；详情见修复记录。

### 2.2 历史摘要把想要完成的动作写成已经完成的事实

旧摘要提示词要求模型总结“做过的动作、经过的地标”，但输入来自选路理由和执行前的画面，不是完成验证结果。

~~~text
选择理由：准备向左移动，经过门口
下发命令：移动 2.0m
实际回执：位移 0.0m，有碰撞

旧风险：摘要仍可能写成“已经过门口”
新记录：保留意图，但实测位移为 0.0m；不宣布经过完成
~~~

**解决方法：** 删除两次摘要调用。历史显式区分动作前观测、未经验证的选择理由、下发的角度/长度与实际位移/碰撞。缺失或不匹配的回执记为未知，不能写成零位移。只提取可观测字段，不把评测真值目标距离放入选路提示词。

**实施中处理的问题：** 回退动作没有对应候选相机图像，不能沿用解析方向编号的旧摘要代码。现在普通移动和 MOVE_BACK 共用结构化历史入口，保留 `synthetic_action` 标记。长场景描述截断时另外保留 RAM 标签，避免挤掉简洁的物体信息。旧测试依赖 trainer 中的具体字面写法，已调整接线检查，并增加真实历史函数的行为测试。

**当前状态：已实现并通过回归测试。** 回执能证明实际位移，但单凭位移仍不能证明穿过指定门口。

### 2.3 选路模型之后还有一个不了解当前验证反馈的模型仲裁

旧多候选分支会再调用模型合并理由、重新决定方向，但该仲裁提示词并未获得相同的 ACN 当前动作反馈，可能覆盖之前的判断。

**解决方法：** 保留现有调用接口和日志事件名称，内部改为确定性候选投票与合法性检查。不生成新的模型理由；默认单次选路直接沿用原候选。STOP 只是提案，MOVE_BACK 仍须当步明确提供，最终执行仍经过原有动作与停止链。融合/验证的耗时日志归类为 `deterministic`、`llm_calls=0`。

**当前状态：已实现。** 多采样同票时保持原样本顺序，是可复现的简单选择规则，不代表已证明最优。

### 2.4 当前动作无法验证，模型可能误以为应该不断重做动作

~~~text
当前要求：Go through the doorway
反馈：cross 验证器尚未实现

不能推出：机器人肯定没有穿门，应不断回到门前重试
也不能推出：把该动作直接标成完成
~~~

**解决方法：** 选路提示词区分“证据不足”“尚未完成”和“验证器缺失”。允许结合近期真实运动与画面选择有用的后续移动，但不得改写 ACN 完成记录。保留原指令作为任务依据，解析计划只是一种解释；计划有冲突时不能服从捏造的目标或关系。

还明确区分候选方向与图内物体方向：编号相对于机器人当前朝向，图内 left/right 相对于那一台相机。候选图片拍摄于当前位姿，不是机器人抵达 waypoint 后的照片。

**当前状态：提示词已修改，能否减少重复动作待在线实验。** 提示词不能补出尚未实现的 cross/pass/traverse 验证器，也不能保证解决路线卡住的问题。

### 2.5 视觉模型被要求给出超出图像证据范围的结论

原提示词中的“可能的最终目标”和“看起来在目标旁边”不够清楚；场景描述还要求生成物体的米制距离。这些文字容易被后续模块当成已经验证的事实。

~~~text
画面：能看到一个门口
候选移动长度：2.0m

不能据此判断：就是指令中那个门口、距离该目标不足 3m、已经穿门完成
~~~

**解决方法：** 候选图像和当前全景两个 Qwen 视觉提示词统一说明：

- 多方向图是同一时刻的观察，不能充当动作前后证据。
- waypoint 长度不是目标距离，Qwen 此处没有标定后的目标深度输入。
- 目标必须符合指令中的身份和空间关系，不能仅凭同类别物体就确认。
- 到达线索与目标方向必须绑定同一目标；不确定时使用 false / JSON null，并注明歧义。
- `arrival_evidence` 只描述局部视觉位置线索，不是成功或正式 STOP 的授权；`confidence` 不是经过校准的成功概率。

SpatialBot 场景描述改为物体、开口、相对布局和有依据的定性远近，不再要求生成看似精确的米制距离。原有 RGB-D 距离验证链和 RAM 标签没有删除，STOP 阈值也未调整。

**当前状态：提示词边界已统一，可靠性提升尚未验证。** 这些文字约束不能让视觉模型变成可靠的距离计或目标实例跟踪器，也没有解决所有高置信度误识别。

## 四、下一步：固定 EP10 诊断测试

建议先跑 EP10，不直接扩到 EP100。使用与上次相同的十个 episode：244、218、226、371、602、1092、748、116、513、11。白名单固定样本集合，实际遍历顺序由数据加载器决定。

建议先在终端执行 `tmux new -s llm_ep10`，然后在新会话中运行：

~~~bash
source /root/miniconda3/etc/profile.d/conda.sh
conda activate opennav
cd /root/My-Experiment

export OPENNAV_LLM_BASE_URL="http://127.0.0.1:23333/v1"
export OPENNAV_LLM_MODEL="/root/models/Qwen3.5-4B"
export OPENNAV_LLM_CLIENT_MODEL="Qwen/Qwen3.5-4B"
export OPENNAV_LLM_API_KEY="not-needed"
export OPENNAV_EPISODE_IDS="244 218 226 371 602 1092 748 116 513 11"

EPISODE_COUNT=10 \
EXP_NAME="instruction_two_stage_ep10_$(date +%Y%m%d_%H%M%S)" \
bash run_OpenNav.bash
~~~

前提是本地 Qwen 服务已就绪。如果启动预检提示连接失败，先在项目目录运行 `bash serve_qwen.sh status`；未启动时执行 `bash serve_qwen.sh start`，就绪后再跑上述测试，不要跳过预检。探活本身会有一次极短的模型请求。

本次不需要删旧缓存。日志在项目根目录 `logs/navigation_records/ep10/实际日期/`；评测结果在 `logs/eval_results/ep10/实际日期/实验名/`。以后恢复非固定集合实验时执行 `unset OPENNAV_EPISODE_IDS`。

重点检查：两步计划是否保留动作关系和终点身份、EP513 是否仍被推离成功区域，以及正式误停/预算结束的分布。候选先验配置保持本次实验之前的值，以观察指令解析链改动的效果。解析检查通过并不代表 SR 已恢复。
