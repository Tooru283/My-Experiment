# 当前全链路输入输出图解

> 本文以 2026-09-03 当前代码为准，描述实际运行的数据流，不把规划中的 M4
> 结构写成已实现功能。每个箭头都说明上游输出、数据格式和直接消费者。

## 0. 阅读约定与智能体

```text
Habitat 室内三维场景
         │ RGB / Depth / navigable candidates
         ▼
   ┌──────────────┐
   │ 虚拟导航智能体 │
   └──────┬───────┘
          │ action 4: angle + distance
          │ action 0: committed STOP
          ▼
    NavMesh 平面移动
```

智能体是 Habitat NavMesh 上的虚拟导航载体，不是人形机器人，没有手臂、腿部
步态或抓取动作。

本文区分三类数据：

- 在线事实：RGB-D、候选、智能体自身 position/heading、动作回执；
- 在线决策：ACN progress、终点证据、STOP proposal/decision、动作命令；
- 离线审计：distance_to_goal、success、SPL、nDTW 等评测字段，不能返回在线决策。

## 2. Episode 初始化链

### 2.1 指令、动作与地标

```text
Habitat episode.instruction
          │ str
          ▼
Open_Nav.get_actions（本地 Qwen3.5-4B 或 云api）
          │ actions: str，换行分隔
          ▼
Open_Nav.get_landmarks（本地 Qwen3.5-4B 或 云api）
          │ landmarks: str，换行分隔
          ▼
actions_cache.json
```

示例：

```text
actions:
Go through the door
Turn left
Go to the left of the stairs
Stop in the doorway to the left of the white double doors

landmarks:
door
stairs
white double doors
doorway
```

直接消费者：

| 输出 | 格式 | 消费者 |
|---|---|---|
| `instruction` | `str` | 分解器、视觉证据、Navigator、日志 |
| `actions` | `str` | Anchor Chain、ACN、Navigator、legacy prompt 兼容层 |
| `landmarks` | `str` | Anchor Chain、视觉验证器、LandmarkPool、Navigator |

LLM completion 进度判断已经停用；本地 Qwen仍用于动作/地标分解、视觉证据和
Navigator 候选选择。

### 2.2 Anchor Chain v2

完整输入：

```text
actions:
Go through the door
Turn left
Go to the left of the stairs
Stop in the doorway to the left of the white double doors

landmarks:
door
stairs
white double doors
doorway
```

输入类型：

```python
actions: str | list[str]
landmarks: str | list[str]
```

```text
actions + landmarks
       │
       ▼
build_anchor_chain(actions, landmarks)
       │ AnchorChainResult: dict[str, Any]
       ├─ anchors[]：3 个非 STOP 路线步骤
       └─ terminal_policy：独立的最终停止目标
```

下面是当前代码对这组输入产生的完整实际输出。使用 `jsonc` 注释标注每个字段的
类型和含义；实际运行时输出是普通 JSON，不包含注释。

```jsonc
{
  // string：Anchor Chain schema 版本。
  "schema_version": "opennav.anchor_chain.v2",

  // array<object>：按执行顺序排列的非 STOP 路线 Anchor。
  // STOP 指令不会进入此数组。
  "anchors": [
    {
      // integer：路线 Anchor 下标，从 0 开始。
      "idx": 0,

      // string | null：从 landmarks 中按字面匹配到的地标。
      "landmark": "door",

      // string | null：动作文本中识别到的房间/区域。
      "room": null,

      // string | null：动作文本中识别到的动作动词。
      "action": "go",

      // string：原始动作文本，用于回放和审计。
      "raw": "Go through the door",

      // boolean：是否为 anchors 路线队列中的最后一个 Anchor。
      // false 不代表该动作未完成，只表示后面还有路线 Anchor。
      "terminal": false,

      // string：Anchor 类型；此处是可视觉匹配的物体地标。
      "kind": "object",

      // string | null：ACN L1 实际匹配和推进使用的标准 key。
      "key": "door",

      // string：结构化解析状态。
      "parse_status": "parsed",

      // object：该 Anchor 的验证合同。
      "verification": {
        // string：由 RAM tag 与候选 waypoint 距离验证物体接近。
        "predicate": "object_nearby",

        // object：object_nearby 的参数。
        "parameters": {
          // float，单位 m：候选 waypoint 可接受的最大距离。
          "max_waypoint_distance_m": 3.0,

          // integer：连续命中多少步后确认 Anchor。
          "min_consecutive_hits": 2
        },

        // string：证据不足时不推进，也不强行判失败。
        "on_unverifiable": "abstain"
      },

      // boolean：该路线 Anchor 本身是否兼任最终目标。
      // 因为存在独立 STOP directive，所以这里为 false。
      "terminal_target": false
    },
    {
      "idx": 1,                         // integer
      "landmark": null,                 // string | null；纯转向没有地标
      "room": null,                     // string | null
      "action": "turn",                // string | null
      "raw": "Turn left",              // string
      "terminal": false,                // boolean；后面仍有路线 Anchor
      "kind": "direction",             // string；方向动作
      "key": "left",                   // string；L1 使用的方向 key
      "parse_status": "parsed",        // string
      "verification": {                 // object
        "predicate": "odometry_motion",// string；用位姿/朝向变化验证
        "parameters": {
          "min_consecutive_hits": 1      // integer；方向动作只需一次命中
        },
        "on_unverifiable": "abstain"    // string
      },
      "terminal_target": false           // boolean
    },
    {
      "idx": 2,                         // integer
      "landmark": "stairs",            // string | null
      "room": null,                     // string | null
      "action": "go",                  // string | null
      "raw": "Go to the left of the stairs", // string

      // boolean：它是 anchors[] 中最后一个路线 Anchor。
      // 注意：这不表示 stairs 是最终 STOP 目标。
      "terminal": true,

      "kind": "object",                // string
      "key": "stairs",                 // string | null
      "parse_status": "parsed",        // string
      "verification": {                 // object
        "predicate": "object_nearby",  // string
        "parameters": {                 // object
          "max_waypoint_distance_m": 3.0,// float，单位 m
          "min_consecutive_hits": 2      // integer
        },
        "on_unverifiable": "abstain"    // string
      },

      // boolean：最终目标由独立 terminal_policy 表示，因此为 false。
      "terminal_target": false,

      // boolean：该最后路线 Anchor 后面紧跟独立 STOP directive。
      "terminal_predecessor": true
    }
  ],

  // integer：anchors 数量。STOP directive 不计入。
  "n_anchors": 3,

  // integer：输入 landmarks 列表数量。
  "n_landmarks": 4,

  // integer：被路线 Anchor 或 terminal target 使用过的地标数量。
  // 本例为 door、stairs、doorway；white double doors 尚未成为独立结构字段。
  "n_landmarks_aligned": 3,

  // float：带可 ground target（landmark 或 room）的路线 Anchor 比例。
  // door 和 stairs 可 ground，Turn left 没有 landmark/room，所以是 2/3。
  "alignment_coverage": 0.6666666666666666,

  // object<string, integer>：各类路线 Anchor 的数量统计。
  "kind_counts": {
    "location": 0,
    "object": 2,
    "direction": 1,
    "unknown": 0
  },

  // boolean：是否没有生成任何路线 Anchor。
  "degenerate": false,

  // object：独立于路线 anchors 的最终停止策略。
  "terminal_policy": {
    // boolean：是否检测到 Stop/Wait/Stay 等终止指令。
    "present": true,

    // array<string>：保留完整原始终止文本。
    "directives": [
      "Stop in the doorway to the left of the white double doors"
    ],

    // string | null：从终止文本中最早匹配到的目标地标。
    // doorway 才是最终目标；不是 anchors[2] 的 stairs。
    "target": "doorway",

    // string：最终目标不能直接 STOP，必须走统一协调链。
    "predicate": "coordinated_stop",

    // array<string>：提交 goal STOP 前必须满足的逻辑条件名称。
    "requires": [
      "chain_complete",
      "all_previous_verified",
      "final_target_evidence",
      "stop_coordinator_allow"
    ],

    // boolean：最终目标不进入 ACN L1 的 anchors 进度队列。
    "in_progress_queue": false
  }
}
```

### 2.2.1 三个路线 Anchor 如何消费

```text
Anchor 0
raw="Go through the door"
kind="object", key="door"
       │ RAM tag + waypoint distance，连续 2 步
       ▼
验证通过后 j: 0 → 1

Anchor 1
raw="Turn left"
kind="direction", key="left"
       │ agent heading / odometry motion
       ▼
验证通过后 j: 1 → 2

Anchor 2
raw="Go to the left of the stairs"
kind="object", key="stairs"
       │ RAM tag + waypoint distance，连续 2 步
       ▼
验证通过后 j: 2 → 3
       │
       ▼
route_progress_complete=true
```

当前 `object_nearby` 主要验证 stairs 是否接近，并没有把 `left of stairs` 的空间
关系拆成独立 predicate。因此该 Anchor 保留完整 `raw` 文本供 Navigator 使用，
但 ACN L1 的结构化验证 key 仍只是 `stairs`。

### 2.2.2 最终目标如何消费

```text
terminal_policy.target="doorway"
terminal_policy.directives=[完整 STOP 文本]
           │
           ▼
VisualTargetVerifier / direction alignment
           │
           ▼
Depth + TerminalInstanceTracker + TerminalEvidenceMemory
           │
           ▼
terminal_target_confirmed
```

最终合取：

```python
goal_complete = (
    route_progress_complete
    and terminal_target_confirmed
)
```

字段 `anchors[2].terminal=true` 只表示 stairs 是路线队列末项；真正的最终停止目标由
`terminal_policy.target="doorway"` 表示。

### 2.2.3 `white double doors` 当前在哪里

输入 landmarks 的顺序为：

```text
door → stairs → white double doors → doorway
```

但 Anchor Chain 当前只把终止文本中最早出现且属于 landmarks 的词作为 target。
在：

```text
Stop in the doorway to the left of the white double doors
```

中，`doorway` 比 `white double doors` 更早出现，因此：

```text
terminal_policy.target = "doorway"
```

`white double doors` 当前：

- 仍存在于原始 `landmarks`；
- 仍存在于完整 `terminal_policy.directives` 文本；
- 会继续提供给 Visual Evidence 和 Navigator；
- 但尚未被 Anchor Chain v2 显式拆成 `relation/reference` 字段。

也就是说，当前代码能保存“doorway to the left of the white double doors”的完整文本
语义，但结构化合同只明确了 `target="doorway"`。未来若扩展合同，更完整的形式应为：

```jsonc
{
  "target": "doorway",                // string | null
  "relation": "left_of",             // string | null；当前尚未实现
  "reference": "white double doors"  // string | null；当前尚未实现
}
```

```text
anchors[]
  ├─► ConstraintQueueLocator（路线推进）
  ├─► LandmarkPool（词表与跨步地标事实）
  └─► RouteState.plan

terminal_policy
  ├─► VisualTargetVerifier（最终目标词和完整 directive）
  ├─► TerminalInstanceTracker / Goal Progress Join
  └─► RouteState.plan
```

STOP 子句不进入 ACN 路线队列，因此：

```text
route_progress_complete=true
        ≠
terminal_target_confirmed=true
```

## 3. 每步 Observation 与候选数据

```text
Habitat observations + get_agent_info

```

`ObservationFrame` 合同：

```python
ObservationFrame(
    episode_id: str,
    step_id: int,
    instruction: str,
    plan_ref: str | None,
```

### 6.3 TerminalInstanceTracker

```text
target terms + supporting landmarks
+ target_direction_id + local_surface_depth_m
+ agent position + heading
                    │
                    ▼
          TerminalInstanceTracker
                    │ terminal_instance_track: dict
```

核心输出：

```json
{
  "instance_key": "513:terminal-instance:4",
  "previous_instance_key": "513:terminal-instance:4",
  "same_instance": true,
  "instance_changed": false,
  "consecutive_observations": 2,
  "target_point": [0.79, 5.67],
  "position_delta_m": 2.15,
  "target_terms": ["entrance to the dining room"],
  "supporting_landmarks": ["white sofas", "fireplace"],
  "weak_generic_target": false,
  "context_overlap": 1.0,
  "distinctive_context_match": true,
  "confirmed_instance_switch": false
}
```

当前关联规则：

```text
所有目标：target_terms 必须一致

弱通用目标（archway / door / room / hall ...）
  └─ target-point delta <= 2.25m

有区分性目标
  └─ delta <= 3.5m
     OR context_overlap >= 0.5
     且 delta <= 5.0m 硬边界

确认实例切换
  └─ target_terms 改变 OR delta > 5.0m
```

标准 persistence 不再读取“两帧 visible”布尔窗口，而是要求同一
`instance_key` 的 `consecutive_observations >= 2`。

### 6.4 弱通用路线成熟度与极近通道

弱通用目标额外读取实际执行后的里程：

```text
non_collision_forward_steps >= 4
AND cumulative actual displacement >= 6.0m
```

`weak_generic_close_is_confirmed()` 极近距离单帧确认只在全部条件成立时启用：

```text
weak_generic_terminal
AND route_progress_complete
AND route_maturity_satisfied
AND direction_aligned
AND 原始当前视图文本已佐证
AND arrival_evidence
AND confidence >= 0.9
AND local_surface_depth_m <= 1.5m
```

它用于减少已到终点但来不及获得第二帧的漏停；不能绕过路线完成和成熟度。

### 6.5 TerminalEvidenceMemory

```text
direct terminal confirmation
          │
          ▼
TerminalEvidenceMemory
          │ confirmed / reused / cache status
          ▼
Goal Progress Join
```

缓存合同：

```text
TTL <= 2 steps
agent displacement <= 2.25m
current visual identity support = true
相同 instance_key 才能 reused=true
```

实例 key 抖动分两种：

- `confirmed_instance_switch=true`：立即清除旧缓存；
- 普通 key 变化：记录 `uncertain_instance_switch_cache_retained`，本步不复用，
  但旧缓存保留到 TTL/位移自然失效。

典型输出：

```json
{
  "confirmed": true,
  "direct_confirmed": false,
  "reused": true,
  "instance_key": "513:terminal-instance:4",
  "cached_instance_key": "513:terminal-instance:4",
  "cache_cleared_reason": null,
  "age_steps": 1,
  "displacement_m": 1.25,
  "max_age_steps": 2,
  "max_displacement_m": 2.25
}
```

## 7. Goal Progress Join

```text
ProgressUpdate(route only)
       +
TerminalEvidenceMemory.confirmed
       │
       ▼
ACNL1ProgressProvider.apply_terminal_evidence
       │ ProgressUpdate(final)
```

唯一正式语义：

```python
goal_complete = (
    route_progress_complete is True
    and terminal_target_confirmed is True
)
```

输出示例：

```json
{
  "route_progress_complete": true,
  "terminal_target_confirmed": true,
  "goal_complete": true,
  "evidence_refs": [
    "progress_locator:9",
    "visual_target_verifier:9",
    "visual_persistence:9",
    "terminal_spatial_evidence:9",
    "terminal_evidence_memory:9"
  ]
}
```

事件顺序：

```text
completion_estimation / pipeline_progress_update
  └─ 路线阶段 ProgressUpdate

goal_progress_update / pipeline_goal_progress_update
  └─ 路线 + 终点证据合取后的最终 ProgressUpdate
```

事件名 `completion_estimation` 是兼容名称，不表示仍在调用 LLM completion。

## 8. Navigator、STOP 与统一仲裁

### 8.1 Navigator 移动决策

```text
instruction + actions + landmarks
+ history_traj + ProgressUpdate.display_text
+ observe_dict + candidate ids
                  │
                  ▼
          Local Qwen Navigator
                  │ Thought + Prediction
                  ▼
       candidate_id | STOP | MOVE_BACK
```

候选可能经过 candidate prior、invalid-candidate fallback、visual ranking、failure
recovery 和 backtrack。动作相关覆盖写入 `DecisionRecord.override_ledger`。

若 `progress_completion` 已提交 STOP，Planner 可以被跳过；否则 Navigator 产生移动
选择或 selector STOP intent。

### 8.2 实际 STOP 来源

```text
goal_complete=true
  └─► progress_completion proposal

Navigator Prediction: STOP
  └─► selector proposal

无合法移动候选
  └─► forced_termination proposal

proactive_terminal_hint
  └─► 仅诊断，decision_effect=false，不产生 proposal
```

### 8.3 StopProposal 与 StopEvidenceItem

```python
StopProposal(
    source: str,
    reason: str,
    route_state_id: str,
    proposal_id: str,
    kind: "goal_stop" | "forced_termination",
    step_id: int,
)
```

每个 goal proposal 当前会适配出：

```text
legacy_combined  兼容日志，不参与正式 required/opposing
v2               正式必需证据
l4               当前 LOG_ONLY，不参与正式裁决
progress         正式必需证据，读取 goal_complete
```

运行时正式策略：

```json
{
  "required_evaluators": ["v2", "progress"],
  "opposing_evaluators": ["v2", "progress"],
  "policy_version": "coordinated_v2.independent_v2_progress"
}
```

因此 `legacy_combined` 出现在 `consumed_evidence_ids` 只表示记录被接收，不表示它
拥有决策权。

### 8.4 StopCoordinator 输出

```json
{
  "decision_id": "244:7:decision_ready:stop",
  "route_state_id": "244:7:decision_ready",
  "step_id": 7,
  "outcome": "commit_goal_stop",
  "selected_proposal_id": "244:7:progress_completion",
  "consumed_evidence_ids": ["...:v2", "...:progress"],
  "rejected_proposal_ids": [],
  "fallback_required": false,
  "policy_version": "coordinated_v2.independent_v2_progress"
}
```

合法 outcome：

```text
commit_goal_stop
commit_forced_termination
reject
no_request
```

同一步先出现 goal reject、随后发现没有合法 movement 时，会将已有 proposals 和
evidence 与 forced-termination proposal 合并后重新仲裁，不再产生冲突异常。

## 9. ActionCompiler 与 Habitat 执行

```text
ResolvedAction + committed StopDecision
                 │
                 ▼
           ActionCompiler
                 │ ActionCommand
                 ▼
           Habitat env.step
```

移动命令：

```json
{
  "action_code": 4,
  "candidate_id": "3",
  "action_args": {"angle": 1.57, "distance": 2.0},
  "stop_requested": false,
  "stop_decision_id": null
}
```

停止命令：

```json
{
  "action_code": 0,
  "candidate_id": "STOP",
  "action_args": null,
  "stop_requested": true,
  "stop_decision_id": "244:7:decision_ready:stop"
}
```

权限边界：

```text
任何模块的 bool / STOP 文本  -X-> action 0
StopCoordinator commit + ActionCompiler ---> action 0
movement/backtrack ResolvedAction + angle/distance ---> action 4
```

`MOVE_BACK` 是 `action_type=backtrack` 的合成控制动作，最终仍由 ActionCompiler
编译成 action 4；历史中记录为 synthetic action，不访问普通候选观察键。

## 10. ActionReceipt、实际位移与审计

`env.step` 后构建：

```python
ActionReceipt(
    receipt_id: str,
    command_id: str,
    episode_id: str,
    step_id: int,
    executed_action: dict,
    candidate_id: str | None,
    collision: float | None,
    done: bool | None,
    steps_taken: int | None,
)
```

合同支持 `pose_before/pose_after/displacement`，但当前 trainer 构造回执时没有传入，
这些字段当前通常为 `null`。实际路线成熟度由回执之后单独再次读取 agent pose 计算：

```json
{
  "event": "route_maturity_odometry",
  "actual_displacement_m": 2.0,
  "collision": false,
  "counted_forward_step": true,
  "cumulative_actual_displacement_m": 8.5,
  "non_collision_forward_steps": 6,
  "position_source": "simulator_agent_pose"
}
```

只有 action 4、非 MOVE_BACK、无碰撞且实际位移大于 0.05m 才累计成熟度。

离线评测字段：

```text
distance_to_goal / distance_gain_selected / success
oracle_success / SPL / nDTW / collisions
```

它们可以进入 `action_post_step`、`post_action_progress` 或 `episode_end` 日志，但
`pipeline_contracts.require_oracle_free` 禁止它们进入 ObservationFrame、
DecisionContext、StopProposal、StopEvidenceItem、StopDecision 和 ActionCommand。

## 15. 当前已知边界

1. `local_surface_depth_m` 不是 bbox/mask 内的目标实例深度；完整实例距离仍需检测或
   分割输出与 Depth 像素对齐。
2. TerminalTrack 的 target point 由 direction、局部 Depth 和 simulator agent pose
   估算，仍有投影抖动；当前用弱通用严格阈值、区分性上下文和滞回折中。
3. position/heading 来源是 simulator agent pose。若实验协议不允许 GPS+Compass，需
   改为动作里程计或视觉里程计。
4. L4 当前为 LOG_ONLY，`legacy_combined` 只保留兼容日志，二者均不是正式 STOP 门。
5. forced termination 只有在 movement 集合为空时合法，但上游 movement 集合仍需在
   M4 中进一步收敛为“经过全部过滤后的合法动作集合”。
6. 部分阈值仍硬编码在 trainer/provider，后续应配置化并写入 policy version。
7. `completion_estimation`、`visual_persistence` 等名称是迁移期兼容事件/引用，不代表
   LLM completion 或旧布尔 persistence 仍拥有决策权。

## 16. 最重要的语义边界

```text
看到目标类别
   ≠ 识别出同一个目标实例

目标方向局部 Depth 通过
   ≠ 得到真实 goal distance

完成全部路线 Anchor
   ≠ 已确认最终目标

确认最终目标
   ≠ 任意模块可以直接 STOP

route_progress_complete
   + terminal_target_confirmed
   = goal_complete

goal_complete
   + V2 support
   + StopCoordinator commit
   + ActionCompiler
   = 合法 Habitat action 0
```
