# 运行时账本：一轮 ep100 的 8.68 小时花在哪，哪些能删

> 数据源 = `clean_baseline_v1` 的 `runtime_latency` 事件（13470 条，字段 `operation` / `elapsed_seconds`）。
> **不是估算，是逐调用实测。**

---

## 1. 实测基线

**一轮 ep100 = 8.68 小时 / 721 步 / 2531 次 LLM 调用。四段加起来正好等于全程 → 完全串行，无重叠。**

| 阶段 | 次数 | 小时 | 占比 | 均值 | 每步 |
|---|---:|---:|---:|---:|---:|
| `completion_estimation` | 724 | **3.15** | **36.3%** | 15.7 s | 1.00 |
| `navigator_move_to_next_vp` | 686 | **2.94** | **33.9%** | 15.4 s | 0.95 |
| `visual_evidence` | 724 | **2.08** | **24.0%** | 10.3 s | 1.00 |
| `stop_current_view_evidence` | 397 | 0.51 | 5.9% | 4.6 s | 0.55 |
| `visual_target_verifier` / `stop_evidence_verifier` / `phase_evidence` / `memory` … | 3716 | **0.00** | 0.0% | — | — |
| **合计** | **2531 次计时调用** | **8.68** | 100% | | |

**读法一：所有非 LLM 的 harness 模块加起来是 0.00 小时。** 我们今天新加的 L0/L1/M1/M2/L4 五个模块
全是纯计算，**不会给运行时增加任何可测量的成本**。

**读法二：`navigator_move_to_next_vp` 686 次 < 721 步** —— 有 35 步没走选路器（走了 fallback）。

---

## 2. 逐段裁决：能删吗，靠什么

| 阶段 | 能删吗 | 机制 | 省 |
|---|:--:|---|---:|
| **`completion_estimation`** | ✅ **能，机制已写好** | **L1 约束队列**整体替换（热路径零 LLM）。GTA Alg.1 L17-18 / HAM-VLN 的 C1′ 是另一条路（折进选路 JSON） | **3.15 h (36.3%)** |
| `navigator_move_to_next_vp` | ❌ 不能 | 这是决策本身。⚠ `NAVIGATOR_MAX_TOKENS: 2048` 是被迫调高的（1024 时 9B 因截断产生 **22.4% 空预测 fallback**），**不要靠砍 token 提速** | 0 |
| `visual_evidence` | ❌ 不能简单门控 | 实测**每步都触发停止校验**（721/721；`completion_gate` 1448 次 + `proactive_stop_gate` 568 + `selector_stop_gate` 252），所以"像 tilt view 那样只在停止时才看图"的省法**不成立** | 0 |
| `stop_current_view_evidence` | ⚠ 已是条件触发 | 397/721 步 | 已省 |

**结论：现在唯一能靠已建好的机制删掉的，是 `completion_estimation` 的 3.15 小时。**

→ **8.68 h → 5.53 h（−36%）**

---

## 3. 另一条：并发（与上一条互斥）

`completion_estimation` 吃 `(actions, landmarks, history_traj)`，`visual_evidence` 吃当前候选图 ——
**两者互不依赖**，代码里却是串行的。理论上可省 `min(3.15, 2.08) = 2.08 h`。

⚠ **但两者打同一张 4090 上的同一个 9B 服务**。并发不会真的省掉 2.08 h，实际收益取决于
serving 端有没有 continuous batching（vLLM / lmdeploy 有）。**乐观估计能省一半，即 ~1 h。**

⚠⚠ **而且这条与 §2 互斥**：L1 一旦替换掉 `completion_estimation`，就没有第二个通道可以并发了。
**不要两条都算进收益。**

⚠⚠⚠ **并发有前科**：M1 那轮开 8 并发撞上 API 限额，四轮分别 24/56/16/23 次报错，
**程序不崩、照样给出一张漂亮但有偏的表**（33.3%）。本地服务不同于 API，但
「部分失败比全部失败危险」这条教训通用 —— **并发改动必须带失败计数断言。**

---

## 4. 明确不划算的三条

| 路子 | 为什么不划算 |
|---|---|
| **换推理框架（AirLLM 之类）** | 我们不缺显存（9B 在 24GB 上有富余）；缺的正是它要付出的速度。且**运行时 100% 是推理**，换框架改不了**调用次数** |
| **砍 `NAVIGATOR_MAX_TOKENS`** | 1024 时 9B 空预测 fallback 22.4%（4B 只有 6.9%）。省时间换来 22% 的决策走 fallback，是净负 |
| **砍 `visual_evidence` 的分辨率/候选数** | 现已是 384 px / q70 / MAX_CANDIDATES 5。再砍会动到 V2 停止门的输入质量，而停止门是唯一决策生效的视觉通路 |

---

## 5. 建议

**只做一件：让 L1 真正替换 `completion_estimation`，而不是并排跑。**

⚠ 现在代码里**两者都跑**（`base_il_trainer_llm.py`，L1 决策生效时只是覆盖 `estimation` 字符串）。
这是**故意的** —— 首轮要在同一条 trace 里对比两者，单开关归因优先于省时间。

**所以时间账是分两步兑现的：**

| 轮次 | 配置 | 时长 | 目的 |
|---|---|---:|---|
| R1（对比轮） | `PROGRESS_LOCATOR.LOG_ONLY=False`，**保留** LLM 调用 | 8.68 h | 同 trace 内对比 L1 与 LLM 估计 |
| R2（兑现轮） | R1 过闸门后，跳过 `estimate_completion` | **5.53 h** | 省下 36.3% |

⚠ **R1 之前 L1 还没过自己的闸门**（「每集不同进度取值数 ≥4」实测 2）。
**先过闸门，再谈省时间。**
