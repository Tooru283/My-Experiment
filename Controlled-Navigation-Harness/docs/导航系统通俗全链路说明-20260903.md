# 从一句导航指令到机器人行动：OpenNav 通俗说明

> 日期：2026-09-03  
> 读者：不需要了解代码、强化学习或机器人算法的人  
> 说明：本文用通俗语言解释当前系统实际怎样工作，以及怎样启动一次实验。

## 1. 这套系统在做什么

可以把它想象成一个在虚拟房屋里行走的机器人。

我们给机器人一句话，例如：

```text
Go through the door and turn left. Go to the left of the stairs.
Stop in the doorway to the left of the white double doors.
```

机器人每走一步都会观察周围的图片，判断：

1. 我现在看到了什么？
2. 指令中的前几步完成了吗？
3. 下一步应该往哪个方向走？
4. 我看到的是不是最终目标？
5. 现在是否真的应该停止？

最后，机器人会不断重复“观察—判断—移动”，直到确认到达目标，或者达到最大步数。

## 2. 机器人一开始拿到什么

系统开始一个任务时，主要拿到两类信息：

```text
一条自然语言指令
        +
机器人周围 12 个固定方向的 RGB / Depth 图像对
```

RGB 图片就是普通彩色图片，用来判断门、桌子、楼梯、沙发和房间类型。

Depth 图片记录每个像素大概有多远。人看到的是颜色，Depth 相机看到的是距离。

```text
彩色图片 RGB
  └─ 这里像门、沙发、楼梯还是走廊？

深度图片 Depth
  └─ 这个方向的墙面、门框或家具大约有多远？
```

机器人不是人形机器人，而是 Habitat 三维环境中的虚拟导航载体。它只能在地面上转向、前进或停止，不能抓取物体。

## 3. 用一条完整指令说明

原始指令经过初步整理后，可以得到：

```text
actions:
Go through the door
Turn left
Go to the left of the stairs
Stop in the doorway to the left of the white double doors

landmarks:
door
stairs
white double doors
doorway
```

通俗地说：

```text
要做的动作：
1. 穿过门
2. 左转
3. 到楼梯左边
4. 在目标门洞停止

需要关注的东西：
门、楼梯、白色双开门、门洞
```

这里 `doorway` 放在最后，是因为它来自最后一句停止指令。它不是普通途中地标，而是最终需要确认的目标。


## 4. 系统先把指令变成一张路线清单

系统不会把整句话一次性判断为“完成”或“没有完成”，而是拆成可逐项检查的路线：

```text
路线清单

[ ] 穿过门
[ ] 左转
[ ] 到达楼梯附近

最终停止目标
[ ] 确认白色双开门左侧的门洞
```

前面三项叫作路线 Anchor，可以理解为路上的检查点。

最后的门洞不放进普通路线清单，而是单独作为终点目标。这样可以避免“路线走完了”就立刻停止。

```text
路线走完
   ≠
已经确认最终目标
```

当前系统对这个例子的理解是：

```text
Anchor 1：door
Anchor 2：left
Anchor 3：stairs

Terminal target：doorway
完整终点描述：
Stop in the doorway to the left of the white double doors
```

“白色双开门”目前主要保留在完整终点描述中，帮助视觉模块和导航模型理解“是哪一个门洞”。系统目前还没有把 `左侧` 和 `白色双开门` 完全拆成独立的空间关系字段。

## 5. 机器人每一步怎样观察

每一步开始时，系统读取一圈固定的 **12 个方向**。相邻方向中心相差 **30°**，
12 个方向合计覆盖 **360°**。每个方向同时包含一张 RGB 和一张 Depth，因此一轮
完整环视可以理解为：

```text
12 × RGB image
+
12 × Depth image
=
12 directional RGB-D pairs
```

当前代码中的方向编号和文字范围如下。表中的 Left/Right 都以机器人当前朝向为基准。

| Direction ID | 代码中的名称 | 覆盖角度范围 | 中心方向 |
|---:|---|---|---|
| 0 | `Front` | left 15° ～ right 15° | 正前方 0° |
| 1 | `Font Left` | left 15° ～ left 45° | 左前方 30° |
| 2 | `Left` | left 45° ～ left 75° | 左前方 60° |
| 3 | `Left` | left 75° ～ left 105° | 正左侧 90° |
| 4 | `Rear Left` | left 105° ～ left 135° | 左后方 120° |
| 5 | `Rear Left` | left 135° ～ left 165° | 左后方 150° |
| 6 | `Back` | left 165° ～ right 165° | 正后方 180° |
| 7 | `Rear Right` | right 135° ～ right 165° | 右后方 150° |
| 8 | `Right` | right 105° ～ right 135° | 右后方 120° |
| 9 | `Right` | right 75° ～ right 105° | 正右侧 90° |
| 10 | `Front Right` | right 45° ～ right 75° | 右前方 60° |
| 11 | `Front Right` | right 15° ～ right 45° | 右前方 30° |

`Font Left` 是当前代码中的原始拼写，含义是 `Front Left`。

```text
                         Direction 0
                          Front 0°
                              │
          Direction 2         │         Direction 10
           Left 60°            │          Right 60°
                 ╲             │             ╱
                  ╲            │            ╱
Direction 3 ──────── 机器人当前朝向 ──────── Direction 9
 Left 90°                                  Right 90°
                  ╱                         ╲
                 ╱                           ╲
          Direction 5                    Direction 7
          Left 150°                      Right 150°
                              │
                         Direction 6
                          Back 180°
```

这里必须区分两个数量：

```text
环视传感器方向：固定 12 个
可行走 waypoint 候选：数量可变，只是 12 个方向中的一个子集
```

Waypoint Predictor 会根据 NavMesh 从 12 个方向中找出当前真正可走的候选。某一步
可能只有 4 个可走方向，另一步可能有更多；不能把 12 张环视图理解成 12 个都能走。

每个可行走候选至少包含：

```text
candidate_id: string
angle_rad: float
waypoint_distance_m: float
rgb: image/array
depth: array
```

一条接近真实运行格式的候选示例：

```text
Direction 2 Direction Viewpoint ID: 2 in Step ID: 1
Elevation: Eye Level
Scene Description: The image contains a bathtub, a door, a wall, and a ceiling.
Scene Objects: bath | bathroom | wall | ceiling | pillar | floor | room
Waypoint Distance: 2.0 meters
```

这表示候选 ID 为 `2`，它位于左前方约 **60°** 的扇区，若被选择，动作编译器会
使用该候选对应的精确 `angle_rad` 和 `distance_m`，而不是直接使用表中的 60° 文本。

## 6. 系统怎样看懂图片

每个候选方向的彩色图片会经过两个主要观察模块：

```text
彩色图片
   ├─ 场景描述模块：用一句话描述这个方向
   └─ 物体识别模块：列出门、桌子、楼梯、房间等标签
```

得到的结果可能像这样：

```text
Direction 3 Direction Viewpoint ID: 3 in Step ID: 5
Elevation: Eye Level
Scene Description: The image shows a hallway with a doorway and stairs.
Scene Objects: hallway | doorway | stair | wall | floor
Waypoint Distance: 2.0 meters
```

这些观察会同时交给：

- 路线进度判断；
- 最终目标判断；
- 下一步方向选择；
- 场景记忆和回退模块。

## 7. 系统怎样判断路线走到哪里

ACN 可以理解为机器人的路线检查表管理员。

它按顺序检查：

```text
现在是否已经穿过门？
        ↓
是否已经完成左转？
        ↓
是否已经到达楼梯附近？
```

例如：

```text
Step 1：看到门，但证据只有一次
Step 2：再次看到门且距离合适 → 第一个检查点完成
Step 3：朝向发生左转 → 第二个检查点完成
Step 4：看到楼梯，但距离较远
Step 5：连续看到楼梯且距离合适 → 第三个检查点完成
```

这时系统只会得到：

```text
route_progress_complete = true
```

意思是“路线步骤已经完成”，不是“任务一定完成”。

系统已经不再让大模型负责 completion 进度判断。当前路线进度由 ACN L1 唯一负责，避免两个模块给出互相冲突的进度。

## 8. 系统怎样判断最终目标

路线快结束时，系统会重点检查最终目标。

对于“停在白色双开门左侧的门洞”，系统会检查：

```text
同一个方向里：

文字描述是否出现门洞？
        +
图像判断是否看到最终目标？
        +
是否有到达迹象？
        +
这个方向的 Depth 是否足够近？
```

必须是同一个方向的证据，不能出现：

```text
左边图片看到门洞
+
右边 Depth 很近
→ 错误地拼成一个终点证据
```

系统现在会先确定目标在哪个方向，再读取那个方向的 Depth。

对于普通物体，使用画面中心附近的距离；对于门洞、拱门等开口，中心射线可能穿过开口打到远处墙面，因此会参考较宽区域中的近表面距离。

需要注意：这个距离只是“目标方向附近表面的距离”，不是仿真器直接提供的真实目标距离。

## 9. 系统怎样判断是不是同一个目标

同一间房子里可能有很多门洞。如果机器人连续两步都看到 `doorway`，也不一定是同一个门洞。

因此系统会为当前观察到的目标建立一个临时编号：

```text
513:terminal-instance:4
```

可以把它理解为：

```text
任务 513 中，目前认为这是第 4 个候选终点实例
```

系统会综合：

- 目标名称；
- 目标方向；
- Depth 距离；
- 机器人位置和朝向；
- 周围伴随地标；

判断下一步看到的是否仍是同一个目标。

### 普通、有明显特征的目标

例如：

```text
餐厅入口
+ 两张白色沙发
+ 壁炉
```

即使位置估计有一点抖动，只要周围特征高度一致，系统可以继续认为是同一个入口。

### 弱通用目标

例如只有：

```text
archway
room
door
```

这种目标在一栋房子里可能出现很多次，因此系统更严格，不会只因为附近也有桌子或壁炉就认为是同一个门洞。

## 10. 为什么有短时终点记忆

有时机器人在 Step 8 已经清楚看到目标，但 ACN 到 Step 9 才确认路线走完。

如果完全只看当前一步，就会错过正确停止时机。因此系统允许短暂记住已经确认的终点：

```text
最多保留 2 步
机器人移动不能超过 2.25 米
当前仍要有相同目标的视觉支持
目标实例编号必须一致才能直接复用
```

如果只是位置估计轻微抖动，系统不会立刻删除记忆，但本步也不会冒险确认；记忆会等待下一步或者自然过期。

## 11. 弱通用目标的特殊保护

对于 `archway` 这类容易认错的目标，系统还要求机器人已经走过足够路线：

```text
至少 4 个无碰撞前进步
并且实际累计移动至少 6 米
```

这里统计的是机器人真正移动的距离，不是模型下达的命令距离。撞墙但没有移动，不会增加路线成熟度。

如果满足路线完成、路线成熟、当前方向证据完整，而且目标已经非常近，系统允许一次非常保守的单帧确认：

```text
视觉置信度至少 0.9
目标方向局部距离不超过 1.5 米
当前文字明确支持目标
```

这个通道用于解决“已经到终点，但任务刚好在最大步数结束，没有机会再看第二帧”的情况。


### 11.1 当前实现中的关键数字

下表集中列出当前代码和配置实际使用的主要数值。它们是实验参数，不是自然语言中的模糊说法。

| 项目 | 当前值 | 含义 |
|---|---:|---|
| 固定环视方向 | 12 | 每步采集 12 组 RGB-D，覆盖 360° |
| 相邻方向中心间隔 | 30° | Direction 0～11 的角度间隔 |
| Visual Target Verifier 调用上限 | 1 次/step | 同一步的 proactive 与 completion 检查共享结果 |
| 视觉终点置信度阈值 | 0.90 | 低于该值不能作为强终点证据 |
| 最早允许视觉终点确认的 step | 3 | 前 3 步以前不放行终点确认 |
| 目标方向局部 Depth 上限 | 3.0 m | 超过该距离的目标方向证据会被距离门控拒绝 |
| Depth 中心区域比例 | 0.25 | 普通目标在中心区域取距离；开口类目标使用近表面分位数 |
| 标准实例持续观测 | 至少 2 次 | 同一个 `instance_key` 需连续命中 |
| 弱通用目标空间关联上限 | 2.25 m | `doorway/archway/room` 等目标采用更严格的实例关联 |
| 特征明显目标放宽关联 | 3.5 m 或上下文重合度 ≥ 0.5 | 二者满足其一才可放宽，但仍受 5.0 m 硬上限约束 |
| 终点证据记忆 | 最多 2 steps | 同时要求记忆期间智能体移动不超过 2.25 m |
| 弱通用目标路线成熟度 | ≥ 4 次有效前进且 ≥ 6.0 m | 碰撞或实际位移不超过 0.05 m 的动作不计入 |
| 弱通用目标近距单帧确认 | ≤ 1.5 m | 还要求置信度 ≥ 0.90、路线完成、方向一致和当前文本佐证 |
| 每个 episode 的回退上限 | 2 次 | 避免反复 MOVE_BACK |
| 短/长指令 step limit | 10 / 12 | 动作数不超过 6 时采用 10，否则采用 12 |

`Visual Evidence MAX_CANDIDATES=5` 表示一次送入视觉证据模块的候选图像采样上限，
不是说环境中最多只有 5 个 waypoint，也不改变固定的 12 路 RGB-D 环视。

## 12. 三个完成状态为什么必须分开

当前系统明确区分：

```text
route_progress_complete
路线步骤是否全部完成

terminal_target_confirmed
最终目标是否被视觉和空间证据确认

goal_complete
前两者是否同时成立
```

关系是：

```text
路线完成
   +
终点确认
   ↓
任务完成
```

只有 `goal_complete=true`，系统才可以正式提出“因为完成目标而停止”。

## 13. 大模型怎样选择下一步

如果还不能停止，本地 Qwen 会看到：

- 原始指令；
- 已拆出的动作和地标；
- 历史上走过的方向；
- ACN 当前进度；
- 当前所有可走方向的场景描述；

然后输出：

```text
思考：为什么选择这个方向
预测：候选方向编号
```

它也可能提出 STOP，但 STOP 只是请求，不会直接结束任务。

如果模型选了不存在的方向，系统会尝试从真实候选中选择替代方向。如果检测到走进死路或反复绕圈，还可以执行一次结构化的 MOVE_BACK。

## 14. 谁最终决定停止

所有停止请求都要经过 StopCoordinator。

```text
任务完成产生的 STOP
导航模型提出的 STOP
没有任何合法方向时的强制终止
             │
             ▼
       StopCoordinator
             │
       支持 / 拒绝 / 强制结束
```

正常目标停止必须同时得到：

```text
视觉终点证据支持
+
progress 中 goal_complete=true
```

旧的 `legacy_combined` 和 L4 目前仍会写入日志，但不再拥有正式停止决定权。

proactive 模块目前也只负责提示“可能接近终点”，不会直接提出 STOP。

## 15. 最终动作是什么

StopCoordinator 只作决定，ActionCompiler 才能把决定转换为 Habitat 动作。

```text
继续移动
   ↓
action 4
angle + distance

正式停止
   ↓
action 0
```

例如，移动指令的运行数据可以写成：

```json
{"action":{"action":4,"action_args":{"angle":0.523599,"distance":2.0}}}
```

其中 `0.523599 rad` 约等于 `30°`。正式停止则是：

```json
{"action":{"action":0,"action_args":null}}
```

任何模块都不能绕过 ActionCompiler 直接发出 action 0。

## 16. 执行后系统会做什么

动作交给 Habitat 后，环境返回新的观察和执行结果：

```text
是否碰撞
是否结束
已经走了多少步
新的 RGB / Depth 图片
新的位置和朝向
```

系统会计算这次实际移动了多少米，用于弱通用目标的路线成熟度，然后进入下一轮：

```text
观察 → 更新路线 → 检查终点 → 选择动作 → 执行动作
  ▲                                             │
  └─────────────────────────────────────────────┘
```

`distance_to_goal`、Success、SPL 和 nDTW 等真实评测指标只用于日志和实验统计，不允许拿来替机器人在线决定是否停止。

## 17. 一次运行实例

下面保留模型和日志中实际使用的英文表达，中文只负责解释数据怎样流动。

### 17.1 输入与路线拆解

```text
Instruction:
Go through the door and turn left. Go to the left of the stairs.
Stop in the doorway to the left of the white double doors.

actions:
Go through the door
Turn left
Go to the left of the stairs
Stop in the doorway to the left of the white double doors

landmarks:
door
stairs
white double doors
doorway
```

Anchor Chain 保存途中检查点和独立终点：

```text
anchors: door -> left -> stairs
terminal_target: doorway
terminal_directive: Stop in the doorway to the left of the white double doors
```

### 17.2 某一步的观测与移动

下面是接近实际接口的格式示例，不表示某条日志的逐字复制：

```text
Step ID: 5
Direction 3 Direction Viewpoint ID: 3
Elevation: Eye Level
Scene Description: The image shows a hallway with a doorway and stairs.
Scene Objects: hallway | doorway | stair | wall | floor
Waypoint Distance: 2.0 meters

ProgressUpdate:
current_anchor_index = 2
route_progress_complete = false
terminal_target_confirmed = false
goal_complete = false

Navigator:
Thought: The stairs and doorway are visible on the left; continue toward Direction 3.
Prediction: 3

ActionCommand:
action_code = 4
angle_rad = 1.570796
distance_m = 2.0
```

这里 `Direction 3` 是正左侧约 `90°`；`action_code=4` 表示执行带角度和距离的移动，而不是停止。

### 17.3 到达终点时

```text
ProgressUpdate:
route_progress_complete = true
terminal_target_confirmed = true
goal_complete = true

TerminalEvidence:
target = doorway
confidence = 0.94
target_direction_id = 3
local_depth_m = 1.32
instance_key = 513:terminal-instance:4

StopDecision:
source = completion
outcome = commit_goal_stop

ActionCommand:
action_code = 0
action_args = null
```

这个例子中，路线完成和终点确认同时为真，StopCoordinator 才批准 STOP，随后
ActionCompiler 输出 `action_code=0`，Habitat 结束该 episode。若只有
`route_progress_complete=true`，系统仍会继续移动或观察，不会因为路线清单走完而停止。

## 18. 哪些地方使用本地 Qwen

本地 Qwen3.5-4B 当前主要负责：

```text
把指令拆成动作
提取重要地标
理解当前图片中的终点证据
从候选方向中选择下一步
```

以下模块不依赖大模型自由判断：

```text
Anchor Chain 路线结构
ACN 路线进度
方向与 Depth 对齐
目标实例跟踪
短时终点记忆
goal_complete 合取
STOP 仲裁
动作编码
```

因此，大模型负责理解和选择，规则模块负责维护状态和守住停止边界。

## 19. 怎样运行一次实验

### 19.1 进入项目环境

```bash
source /root/miniconda3/etc/profile.d/conda.sh
conda activate opennav
cd /root/My-Experiment
```

### 19.2 启动本地 Qwen 服务

建议在 tmux 中启动：

```bash
tmux new -s opennav
```

进入 tmux 后执行：

```bash
source /root/miniconda3/etc/profile.d/conda.sh
conda activate opennav
cd /root/My-Experiment
bash serve_qwen.sh
```

等服务启动完成后，按：

```text
Ctrl+b，然后按 c
```

这会在同一个 tmux 会话中新建窗口，用于运行导航实验。

### 19.3 先运行 EP10

```bash
source /root/miniconda3/etc/profile.d/conda.sh
conda activate opennav
cd /root/My-Experiment

EPISODE_COUNT=10 \
EXP_NAME=terminal_track_v3_ep10_$(date +%Y%m%d_%H%M%S) \

```

### 19.4 运行 EP100

```bash
source /root/miniconda3/etc/profile.d/conda.sh
conda activate opennav

EPISODE_COUNT=100 \
EXP_NAME=terminal_track_v3_ep100_$(date +%Y%m%d_%H%M%S) \

```

### 19.5 让任务在断开 SSH 后继续

实验开始后，按：

```text
Ctrl+b，然后按 d
```

这是退出 tmux 显示但保留任务运行。之后可以检查：

```bash
tmux ls
```

重新进入：

```bash
tmux attach -t opennav
```

如果 `tmux ls` 显示：

```text
no server running on /tmp/tmux-0/default
```

说明当前没有 tmux 会话，任务可能是在普通终端中启动的。

## 20. 日志在哪里

导航主日志：

```text
/root/My-Experiment/logs/navigation_records/ep10/<日期>/
/root/My-Experiment/logs/navigation_records/ep100/<日期>/
```

结构化 JSONL 与同名 `.log` 放在一起。JSONL 更适合统计每一步发生了什么。

其他常用日志：

```text
logs/harness_traces/       模块级 trace
logs/eval_results/         评测结果
logs/running_log/          运行控制日志
logs/qwen_server/          本地 Qwen 服务日志
```

实时查看最新导航日志可以使用：

```bash
tail -f /root/My-Experiment/logs/navigation_records/ep100/$(date +%Y%m%d)/*.log
```

查看 GPU：

```bash
nvidia-smi
```

检查导航进程：

```bash
ps aux | grep -E "run.py|run_OpenNav" | grep -v grep
```

## 21. 怎样判断一次运行是否正常

首先看运行稳定性：

```text
没有 Traceback
没有 navigation_error
每一步最多一次 Visual Target Verifier
没有 proactive_visual STOP proposal
MOVE_BACK 不产生 KeyError 或 ValueError
```

然后看行为：

```text
正确终点能够产生 goal_complete=true
明显错误的远距离目标不会 STOP
selector 的随意 STOP 会被拒绝
forced termination 只在没有合法移动方向时出现
```

最后再看整体指标：

```text
Success Rate
SPL
nDTW
平均最终距离
step-limit 比例
显式 goal STOP 数量
```

## 22. 当前系统还不完美的地方

这套逻辑不追求每一步完全无错，目前仍有这些边界：

1. Depth 是目标方向的局部表面距离，不是目标 mask 内的精确距离。
2. 门洞、房间等通用目标仍可能被视觉模型认错。
3. `left of the white double doors` 尚未完全拆成结构化空间关系。
4. 目标实例位置由方向、Depth 和智能体位姿估计，会有抖动。
5. 一部分旧日志名称和兼容逻辑仍要在 M4 阶段清理。
6. 导航模型可能选择绕路、回头或在正确目标附近没有及时 STOP。

当前设计的目标不是保证零错误，而是做到：

```text
错误停止有明确安全门
正确停止不会被无限压制
每次决定都有日志可查
大规模 EP100 可以暴露真实统计问题
```

## 23. 一句话总结

```text
系统先把一句话变成路线检查表，再用多方向 RGB-D 图片不断确认自己走到哪里；
本地 Qwen负责理解图片和选择方向，ACN 负责路线进度，TerminalTrack 负责确认终点实例，
StopCoordinator 负责决定能否停止，ActionCompiler 最终把决定变成环境动作。
```
