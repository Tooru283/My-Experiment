# 指令两步解析修复与验证

记录时间：2026-09-08。针对 `llm_roles_v1_ep10_20260908_100921` 中暴露的指令解析问题，恢复两个顺序模型请求，并修正停止位置在各模块之间的传递。本次候选先验、视觉提示词、STOP 阈值均保持原配置，便于后续比较解析链改动的影响。

## 一、问题：合法 JSON 仍然可能改变导航任务

EP513 原指令：

```text
Go into the living area with the fireplace.
Stop in the area between the two white sofas,
next to the entrance to the dining room.
```

原联合解析将后一句拆成两个 STOP。后续停止目标变成了餐厅入口，丢失了“停在两个沙发之间”的主体位置。这个错误有明确日志依据；但仅凭这一次 EP10，不能确定它对整体性能下降的贡献一定大于选路或视觉问题。

## 二、解决方法：先完整动作，再地标与停止位置

### 2.1 第一步只提取动作

输入原始指令，输出只有 `actions: list[str]` 的 JSON。保留原文修饰语和条件，不允许把一个停止要求变成两个。

```json
{
  "actions": [
    "Go into the living area with the fireplace",
    "Stop in the area between the two white sofas, next to the entrance to the dining room"
  ]
}
```

程序检查停止动词数量和完整最终停止原文。若模型把“进入房间并停下”保留在一项里，程序从明确的 STOP/wait 位置无损分开移动与停止；停止条件内的逗号不产生新 STOP。普通动作中，明确的 `and + 动作动词` 可以分开；带 `until/while/after/before` 的项保留，`Turn right to walk past stairs` 也保留。

### 2.2 第二步同时读取原指令和第一步动作

第二步输出 `landmarks: list[str]` 和 `terminal_target: str | null`。原指令继续提供依据，避免第一步的信息损失完全传给第二步。

```json
{
  "landmarks": [
    "living area with the fireplace",
    "two white sofas",
    "entrance to the dining room",
    "area between the two white sofas"
  ],
  "terminal_target": "area between the two white sofas"
}
```

其中 `entrance to the dining room` 是参照物，`area between the two white sofas` 是主停止位置。主停止位置必须位于地标列表末尾，与现有停止检查接口一致。没有明确停止要求时，`terminal_target` 使用 JSON null。

程序检查主停止位置与原句对应，并检查最终条件中的参照物和修饰词是否保留。当前规则覆盖明确的常见英语停止句式；它是原文保留检查，不能当作通用自然语言语义验证器。

### 2.3 传给 ACN 的接口保持一致

两个阶段检查完成后，仍返回原有的两段逐行文本 `actions, landmarks`。完整终点关系保存在停止动作中，主停止位置在地标列表末尾。

EP513 对应的下游结果：

```text
ACN 路线队列：Go into the living area with the fireplace
terminal_policy.directives：一个完整 STOP 条件
terminal_policy.target：area between the two white sofas
final_landmark_terms：area between the two white sofas
```

`terminal_target` 是解析阶段的身份描述，不代表目标已被观察到，更不代表机器人已经到达。ACN 完成验证和正式 STOP 证据链继续负责各自的判定。

## 三、实施时遇到的问题与处理

| 问题 | 处理 |
|---|---|
| 补丁工具无法启动容器命名空间，前次修改未落盘 | 找到容器内已有的 `apply_patch` 程序，在获准的项目目录应用补丁并检查写入结果 |
| 只改提示词会继续使用旧错误缓存 | 版本更新为 `opennav.instruction_plan.v2.two_stage`；缓存指纹包含两个提示词、模型、地址和版本；保留旧缓存但不复用 |
| 第一版校验要求 STOP 必须已经单独成项，误拒“进入房间并停下” | 在完整停止原文保留的前提下，程序分开明确的移动与停止边界 |
| Qwen 把“门口及其左侧关系”整个写成终点名称 | 分离原文里的主停止位置和参照物；完整关系仍保留在停止动作中 |
| 同时保留长短两个终点名称时，ACN 偏好长名称，旧停止模块取末尾短名称 | 将长描述中的参照物单独保留，统一主终点名称，并增加跨模块一致性回归测试 |
| 模型输出仍可能非法或丢失停止条件 | 每阶段最多一次带具体错误原因的纠错请求；持续失败时中止，不缓存半份计划，不悄悄猜测终点 |
| 固定记录一次调用会掩盖真实开销 | 正常两次请求；发生纠错时最多四次；逐阶段记录原始响应、校验结果、耗时及实际调用次数 |

`instruction_plan_parsed` 导航 JSONL 事件记录两个阶段的数据；失败使用 `instruction_plan_failed`。底层网络重试可能额外产生 HTTP 请求，以上次数指逻辑提取调用。

## 四、验证范围

回归测试覆盖：EP513 单 STOP、缺失 doorway、丢失左右关系、联合 tub/sink、非法第一阶段阻止第二阶段、有限纠错、缓存隔离，以及 ACN 与最终地标读取的一致性。

同时对本地 Qwen3.5-4B 执行固定 EP10 的十条原始指令提取，直接调用实际导航类的解析方法，随后交给实际 Anchor Chain 与地标读取函数；不启动 Habitat，不写实验缓存。

最终结果：**119 项自动化回归通过；真实 Qwen 的 10/10 条指令通过本次原文保留与跨模块终点一致性检查。** 共 20 次逻辑请求，无纠错重试，模型请求耗时合计约 34.66 秒（平均每条指令 3.47 秒；不是每个导航 step 的耗时）。相关 Python 编译和 `git diff --check` 通过。

这不是“全部动作语义正确率 100%”。例如实际输出仍包含 `Leave the bathroom and closet` 这样的多区域动作，以及 `bed room` / `bath room` 的原文拼写；本轮没有证明下游验证器能完整处理这些路线表达。

本轮只验证解析输出与接口，**不产生新的 SR/SPL/OSR**。两步解析是否改善导航成功率，需要相同 EP10 的在线导航对照。路径中的动作含义、拼写别名、cross/pass 验证缺口，以及视觉不稳定仍可能影响表现。
