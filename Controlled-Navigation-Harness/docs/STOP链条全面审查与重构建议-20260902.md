# STOP 链条全面审查与重构建议（2026-09-02）

## 1. 审查结论

当前 STOP 链已经建立了两个可靠边界：

1. `StopCoordinator` 负责形成正式 `StopDecision`；
2. `ActionCompiler` 是 Habitat `action=0` 的唯一编码出口。

但上游证据仍主要是“目标类别级”而不是“目标实例级”。当前最大风险已经从
多处直接发出 STOP，转变为多个弱证据被合流成错误的 `goal_complete=true`。

总体判断：

```text
单一 STOP 执行出口：可靠
proactive/selector 旁路：基本封闭
运行稳定性：明显改善
目标类别确认：可用
目标实例确认：不足
证据合同一致性：仍需重构
forced termination：存在冲突风险
实验可复现性：阈值配置不完整
```

最新 weak-generic 路线成熟度尚未经过新的 EP10 运行验证。即使它能阻断
EP11 Step 3，也只能作为临时安全门，不能替代目标实例跟踪。当前不建议直接
进入 EP50。

## 3. 高优先级问题

### P0-1：视觉证据没有绑定目标实例

`TerminalEvidenceMemory` 当前保存 step、position 和 evidence，但复用条件只
检查当前仍有视觉支持、证据未超时、智能体位移未超过阈值。

它没有验证当前看到的目标与缓存目标是否为同一个实例：

```text
Step N：看到 archway A
Step N+1：看到 archway B
```

只要类别仍为 `archway`，缓存就可能继续成立。应增加：

```ini
target_instance_key
target_direction_history
scene_signature
supporting_landmarks
observation_frame_id
```

### P0-2：连续视觉确认没有方向或实例连续性

当前持久性是最近两帧 `final_target_visible=true`。它不能证明两帧中：

- 出现的是同一个目标；
- 目标方向连续；
- 空间关系一致；
- 目标实例没有切换。

应以结构化 `TerminalTrack` 代替布尔窗口：

```python
TerminalTrack(
    target_term="archway",
    direction_id=1,
    depth_m=1.8,
    scene_signature="...",
    frame_id="...",
)
```

### P0-3：文本佐证没有与 target_direction_id 对齐

V2 可以输出 `target_direction_id=1`，但当前文本佐证搜索整个全景文本。其他
方向出现同类词也可能为方向 1 提供佐证。

正确条件应为：

```text
Direction 1 文本明确出现目标
+ Direction 1 图像识别出目标
+ Direction 1 Depth 合理
```

三种证据必须绑定同一个 direction ID。

### P0-4：Depth 不是目标实例的 Depth

普通目标使用目标方向中心中位数；开口类目标使用宽区域 20% 近表面深度。
该值仍可能来自家具、墙面、柱子、地板、遮挡物或另一个门框。

因此当前值只能称为：

```text
target-direction local surface depth
```

不能称为目标实例距离。正确方案需要目标检测或分割区域与 Depth 对齐：

```text
目标检测/分割 mask
        │
        ▼
同一区域 Depth 像素
        │
        ▼
target_mask_depth_m
```

## 4. 中高优先级问题

### P1-1：路线成熟度累计命令距离，不是实际位移

当前使用动作命令中的 `distance` 累加。碰撞、未完整执行、原地往复仍可能
增加成熟度。因此“4 次撞墙、命令累计 6m”也可能满足 weak generic 条件。

应改用：

```ini
actual_displacement_m
non_collision_forward_steps
net_displacement_from_route_anchor
scene_region_transition
```

### P1-2：TerminalEvidenceMemory 使用 simulator agent position

缓存局部性依赖 `get_agent_info().position`。它没有读取目标坐标，不属于
`distance_to_goal` 泄漏，但如果实验声明智能体只有 RGB-D 和动作反馈，精确
世界坐标仍可能是特权状态。

处理要求：

- 若基准允许 GPS+Compass，明确记录权限；
- 若不允许，改用 action odometry 或视觉里程计；
- 不应只标记 `oracle_free=true` 而不说明位置来源。

### P1-3：legacy_combined 是循环证据

`legacy_combined` 的 verdict 来自前置控制流计算得到的 `allowed` 布尔值，
而该布尔值本身已经受到 V2、goal state 和 gate 影响。协调器再次要求
`legacy_combined=support` 属于重复确认，不是独立证据。

此外其 reason 声称代表 V2/depth/L4，但 L4 可能为 log-only，语义不准确。

建议删除 `legacy_combined`，改为独立证据：

```text
terminal_identity
terminal_spatial
terminal_persistence
route_progress
terminal_memory
```

### P1-4：L4 oppose 被记录但不影响决策

EP11 和 EP513 都出现过 `l4=oppose`，但当前 L4 不属于运行时必需硬门，STOP
仍可能提交。日志看起来像协调器消费了 L4，实际没有决策作用。

不能直接启用 L4，因为 EP513 正确停止时它也 oppose。应先修复 L4 的证据
来源和 `final_landmark_arrived` 语义，再决定是否升级为硬门。

### P1-5：原始 V2 与派生 verdict 混在同一个对象

通用目标策略会产生：

```ini
raw_v2_verdict = uncertain
verdict = allow
```

但 `reason` 和 `allow_blockers` 可能仍写着该目标被保守规则阻断，导致
`v2=support` 与 reason 相互矛盾。

应拆分为两个不可变合同：

```text
RawVisualVerdict
TerminalPolicyVerdict
```

不能原地改写 V2 结果。

## 5. 控制流问题

### P1-6：forced termination 与已有 reject 决策可能冲突

如果同一步已有 `m3_stop_decision=reject`，随后发现没有合法移动候选并请求
forced termination，当前实现会因已有 StopDecision 而抛出 RuntimeError。

应由协调器一次性接收：

```text
goal_stop proposal
forced_termination proposal
legal movement candidates
```

然后只产生一个最终决策。

### P1-7：协调器使用的 movement candidates 不是真正合法动作集合

当前 goal STOP 仲裁使用 `observe_dict.keys()`，但真正可执行的移动还要求候选
同时存在于 `radius_dict` 和 `distance_dict`。

应传入：

```python
legal_movement_candidate_ids = (
    observe_dict ∩ radius_dict ∩ distance_dict
)
```

否则协调器可能认为仍可移动，随后 ActionCompiler 前才发现无合法动作。

### P1-8：selector STOP 分支仍保留多套历史 rescue 逻辑

当前仍保留 visual rescue、U2 rescue、E3-B override、legacy should_stop、L4
和 coordinator。虽然现有 goal_complete 条件已收紧旁路，但未来修改一个条件
就可能重新开放独立 STOP 权限。

建议 selector 只产生 `StopIntent`：

```text
selector 输出 STOP
        │
        ▼
StopIntent（无执行权限）
        │
        ▼
统一 GoalJoin / StopCoordinator
```

## 6. 配置和可复现性问题

### P2-1：新策略阈值硬编码在 trainer

当前硬编码包括：

```ini
memory_max_age_steps = 2
memory_max_displacement_m = 2.25
weak_generic_min_moves = 4
weak_generic_min_translation_m = 6.0
opening_depth_percentile = 20
opening_depth_region = 0.70
```

建议迁入统一配置：

```yaml
TERMINAL_EVIDENCE:
  MEMORY_MAX_AGE_STEPS: 2
  MEMORY_MAX_DISPLACEMENT_M: 2.25
  WEAK_GENERIC_MIN_MOVES: 4
  WEAK_GENERIC_MIN_TRANSLATION_M: 6.0
  OPENING_DEPTH_PERCENTILE: 20
  OPENING_DEPTH_REGION_FRAC: 0.70
```

同时记录独立 policy version。

### P2-2：配置和注释落后于实现

配置仍描述 center-of-view depth 和 fail-open，但实际 TerminalEvidence 已读取
VLM 目标方向、对开口使用近表面 percentile，并在方向或 Depth 缺失时
fail-closed。旧 proactive 注释也仍存在，但 proactive 已无 STOP 权限。

需要同步代码注释、yaml 说明、运行 metadata 和设计文档。

### P2-3：VLM target_direction_id 缺少严格 schema 校验

目前无效方向通常通过 Depth 缺失被保守拒绝，但仍应在 schema 层验证：

- 必须属于当前 contact sheet 的方向集合；
- 必须与对应方向文本和图像共同绑定；
- 无效值应产生明确 schema error，而不是只表现为 Depth unavailable。

## 7. 其他观察

### P2-4：每步 V2 使用 stop_proposal=true

当前每一步都以“形式上的 STOP proposal”调用 completion V2，但实际此时尚未
生成 pipeline StopProposal。它会触发与 STOP proposal 绑定的 min-step、generic
和 contradiction 规则，造成命名和语义混淆。

建议将其重命名为 `terminal_observation`，由 TerminalPolicy 再决定是否产生
真正的 StopProposal。

### P2-5：forced termination 与 goal STOP 在评测终止原因中可能混淆

两者最终都编码为 Habitat action 0。日志和统计必须保留：

```ini
goal_stop
forced_termination
step_limit
```

否则 operational termination 可能被误认为任务完成 STOP。

## 8. 建议的最终结构

```text
1. TerminalObserver
   输出当前帧原始目标观测
   identity / direction / mask / depth

2. TerminalTracker
   跨帧绑定同一目标实例
   instance_key / continuity / freshness

3. RouteProgress
   输出 ACN route 状态
   complete / transition / route evidence

4. GoalJoin
   唯一生成 goal_complete
   route + tracked terminal + relation

5. StopCoordinator
   只处理 goal_stop、forced_termination、legal movements
```

建议的核心合同：

```python
TerminalEvidence(
    frame_id,
    target_term,
    target_instance_key,
    direction_id,
    identity_verdict,
    text_corroborated_in_direction,
    target_mask_depth_m,
    relation_satisfied,
    persistent_track_length,
    freshness_steps,
    ego_displacement_since_confirmation,
    policy_version,
)
```

GoalJoin：

```python
goal_complete = (
    route_progress_complete
    and terminal_evidence.instance_confirmed
    and terminal_evidence.relation_satisfied
    and terminal_evidence.fresh
)
```

StopCoordinator 不应重新解释 V2、Depth 或缓存，只验证已经版本化的合同。

## 11. P0-1 实施记录：终点视觉证据绑定目标实例

状态：第一阶段已实现，等待真实 EP10 验证。

本次新增 `TerminalInstanceTracker`。它不再用“连续两步的
`final_target_visible=true`”直接代表同一目标，而是将每次终点观测投影为局部二维目标点：

```text
目标词 + 目标方向 ID + 方向 Depth + 智能体位置与朝向
                         │
                         ▼
             ego-local target_point
                         │
          同目标词且空间差 <= 2.25 m
                         │
                         ▼
                 stable instance_key
```

当前约束如下：

1. 只有 `final_target_visible=true`、`arrival_evidence=true` 且方向、Depth、位姿
   完整时才创建实例 key；几何不足时明确 abstain。
2. 连续视觉确认要求同一个 `instance_key` 连续出现至少 2 次。
3. 同类目标若空间位置变化超过 2.25 m，会生成新的实例 key，连续计数从 1 开始。
4. `TerminalEvidenceMemory` 只允许复用相同实例 key 的短时证据。
5. 当前视觉指向另一实例时，旧缓存立即清空，并记录
   `cache_cleared_reason=instance_changed`。
6. `terminal_instance_track` 记录目标点、空间差、连续次数、实例变化原因；
   `terminal_spatial_evidence` 同时记录 `instance_key` 与 `same_instance`。

自动化验证：专项测试 14/14、全量测试 58/58 通过。覆盖同实例跨步匹配、
同类不同实例切换、缓存失效和几何不足时 abstain。

仍需注意：这是基于方向扇区与 Depth 的空间关联，不是像素级实例分割或物体
Re-ID。它先封住“不同同类目标共享 persistence/cache”的 P0 风险；后续若引入
目标 mask，应将 target point 的深度估计从方向区域统计升级为 mask 内深度。


## 12. 其余高优先级问题实施记录

### P0-2：连续视觉确认缺少方向/实例连续性

状态：已随 P0-1 完成。布尔 `recent_ftv_window` 不再拥有终点确认权限；正式
persistence 来自同一 `instance_key` 的 `consecutive_observations >= 2`。

### P0-3：文本佐证与 target_direction_id 未对齐

状态：已修复。新增 `direction_aligned_terminal_result`，正式终点证据只读取
`selected_candidate_verdict`，并要求同一个候选同时满足：

```ini
target_direction_id 非空
final_target_visible = true
arrival_evidence = true
missing_final_landmarks = []
```

全景聚合的 visible/arrival 只保留为 `aggregate_*` 审计字段，不能再为选中方向
提供支持。方向缺失、目标词只出现在其他候选、选中方向没有 arrival 时均 reject。

### P0-4：Depth 不是目标 mask 的 Depth

状态：风险已封闭，完整 mask 方案待感知模块支持。现有字段明确标为
`local_surface_depth_m`，语义记录为
`direction_local_surface_not_instance_mask`；旧 `target_depth_m` 仅作为带 deprecated
标志的兼容字段。该距离必须与稳定实例轨迹共同成立，不能独立生成终点确认。

当前视觉输出没有 bbox/mask，因此不能声称已获得真正的 `target_mask_depth_m`。
彻底解决仍需感知模块输出检测框或分割 mask，并在同一像素区域聚合 Depth。

### P1-1：路线成熟度累计命令距离

状态：已修复。现在在 `envs.step()` 后重新读取智能体位姿，累计
`actual_displacement_m`，仅统计无碰撞且实际位移大于 0.05 m 的 forward step。
日志事件为 `route_maturity_odometry`。位置来源明确记录为
`simulator_agent_pose`，不再标成来源不明的 oracle-free 距离。

### P1-3：legacy_combined 循环证据

状态：已退出正式决策。`StopCoordinator` 的 required/opposing evaluator 改为
`v2 + progress`，policy version 为
`coordinated_v2.independent_v2_progress`。`legacy_combined` 暂时仅作为兼容日志输出，
不再允许或阻止 goal STOP；后续合同清理时可删除该 adapter。

### P1-6：forced termination 与已有 reject 冲突

状态：已修复。同一步已有 `reject/no_request` 时不再抛 RuntimeError，而是把已有
proposal/evidence 与新的 forced-termination proposal 合并，在空 movement 集合上
重新调用一次 `StopCoordinator`。已经提交的 goal STOP 或 forced termination 保持
幂等返回。

验证结果：全量自动化测试 61/61 通过，Python 编译与 diff 格式检查通过。
真实运行仍建议先做 EP10；重点观察方向对齐拒绝率、实例 key 稳定性、实际位移成熟度
以及 forced termination 是否只发生在 movement 集合为空时。
